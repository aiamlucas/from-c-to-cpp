ex00

Polymorphism

Animal, Dog, Cat — and the deliberately broken WrongAnimal/WrongCat pair, built specifically to prove you understand why the first three needed virtual.

New concepts this exercise introduces
subtype polymorphism
Contrasted with Module 02's ad-hoc polymorphism (operator overloading) — this kind is resolved at runtime, by the object's real type, not at compile time.
virtual as the fix to static binding
Without it, calling through a base pointer resolves by the pointer's declared type. virtual flips resolution to the object's actual type.
direct call vs base-pointer call
Calling makeSound() on a named Dog variable proves nothing — the type is already known at compile time. Only a base-pointer call actually tests virtual.

The pitch

"Animal has a virtual makeSound() so Dog and Cat can each override it correctly. The WrongAnimal/WrongCat pair is the same shape with virtual deliberately removed, so I can show the exact failure mode side by side with the working version — a wrong sound, and a skipped destructor."

Walk the code

Animal.hpp header

class Animal {
protected:
    std::string _type;
public:
    Animal(void);
    Animal(const Animal &other);
    Animal &operator=(const Animal &other);
    virtual ~Animal();

    std::string getType(void) const;
    virtual void makeSound(void) const;
};

getType() is required because the subject's own main() calls j->getType() directly — easy to miss on a first pass since it's mentioned only in the example code, not the prose. makeSound() and the destructor are both virtual; this exercise is entirely about the first one, but the destructor matters just as much once ex01 gives Dog/Cat something to actually leak.

WrongAnimal.hpp the deliberate contrast

class WrongAnimal {
protected:
    std::string _type;
public:
    WrongAnimal(void);
    WrongAnimal(const WrongAnimal &other);
    WrongAnimal &operator=(const WrongAnimal &other);
    ~WrongAnimal();                        // deliberately NOT virtual
    std::string getType(void) const;
    void makeSound(void) const;         // deliberately NOT virtual
};

Same shape as Animal, one keyword removed on purpose. WrongCat mirrors Cat identically — the only difference anywhere in these two class hierarchies is the missing virtual.

Fig 1 — same shape, one keyword removed — the entire visible difference between the two hierarchies

main.cpp the subject's own test, extended

int main(void) {
    {
        const Animal *meta = new Animal();
        const Animal *j = new Dog();
        const Animal *i = new Cat();
        std::cout << j->getType() << std::endl; // "Dog"
        std::cout << i->getType() << std::endl; // "Cat"
        i->makeSound(); // Cat's sound — virtual resolves by the REAL object
        j->makeSound(); // Dog's sound
        meta->makeSound();
        delete meta;
        delete j; // ~Dog() then ~Animal()
        delete i; // ~Cat() then ~Animal()
    }
    {
        const WrongAnimal *meta = new WrongAnimal();
        const WrongAnimal *i = new WrongCat();
        i->makeSound(); // WRONG on purpose — prints WrongAnimal's sound, not WrongCat's
        meta->makeSound();
        delete meta;
        delete i; // only ~WrongAnimal() runs — ~WrongCat() never fires
    }
    return 0;
}
Rubric wording, quoted directly

"The WrongCat must output the WrongCat makeSound() only when used as a wrongCat." — i.e. calling wrongCat.makeSound() directly on a named WrongCat variable correctly prints WrongCat's own sound (the compiler already knows the exact type). Only when accessed through a WrongAnimal* does it incorrectly fall back to WrongAnimal's sound. Both behaviors need to be demonstrable in your test.

Questions to expect

Why does calling makeSound() directly on a Dog variable not prove virtual is working?
The compiler already knows dog's exact type at compile time in that case — there's no ambiguity to resolve. Virtual only matters the moment the declared pointer type and the real object type genuinely diverge, which only happens when calling through a base pointer.
What would happen to WrongCat's destructor without virtual on WrongAnimal's?
delete on a WrongAnimal* pointing at a real WrongCat would only ever call ~WrongAnimal() — resolved by the pointer's declared type, same static binding rule as any other non-virtual member function. ~WrongCat() would never run at all.
Why is getType() needed on Animal?
The subject's own example code calls j->getType() directly — it's easy to miss since it's only shown in the code sample, not stated in the prose.
EvalHub rubric — quoted verbatim
"You must be able to instantiate and use this class." (Animal, ex00 specifically)
Yes — Animal is an ordinary concrete class in ex00/ex01; only ex02 makes it abstract.
"They are at least two classes that inherit from Animal: Cat and Dog. The constructor and destructor outputs must be clear."
Yes — every constructor/destructor across Animal, Dog, Cat prints a distinct, identifiable message.
"The attribute type is set to the appropriate value at creation for every animal."
Yes — Dog's constructor sets _type = "Dog", Cat's sets _type = "Cat", both verifiable via getType().
"makeSound() should be virtual! ... virtual keyword is mandatory."
Yes — virtual void makeSound(void) const; in Animal.hpp, confirmed working via the Animal* array test.
"There should be an example with a WrongAnimal and WrongCat that don't use the virtual keyword."
Yes — WrongAnimal.hpp/.cpp and WrongCat.hpp/.cpp, structurally identical to the working pair, virtual removed from both makeSound() and the destructor.
ex01

I don't want to set the world on fire

Brain turns the virtual destructor from an abstract rule into something with real, checkable stakes — a heap allocation that either gets freed correctly or doesn't.

New concepts this exercise introduces
composition alongside inheritance
Dog is-a Animal (inheritance) and has-a Brain (composition) simultaneously — two different relationships, same class.
shallow vs deep copy
The exact Module 02 OCF lesson made concrete: copying a raw pointer shares one resource between two objects; copying the pointed-to contents gives each object its own.
array of Animal* vs array of Animal
A literal array of Animal objects would slice every Dog/Cat down to just its Animal part. The subject means an array of pointers to full, unsliced heap objects.

The pitch

"Dog and Cat now each own a Brain on the heap. The copy constructor and assignment operator both allocate or copy into an independent Brain rather than sharing the pointer, and the whole array test deletes everything through Animal* specifically, so the virtual destructor from ex00 is what's actually freeing every Brain, not me casting back to the real type."

Walk the code

Brain.hpp composition target — not part of the Animal hierarchy

class Brain {
private:
    std::string _ideas[100];
public:
    Brain(void);
    Brain(const Brain &other);
    Brain &operator=(const Brain &other);
    ~Brain();
    void setIdea(int index, const std::string &idea);
    const std::string &getIdea(int index) const;
};

Brain has zero relationship to Animal — no inheritance either direction. This matters for the rubric specifically: "the Brain attribute should not be inside the Animal class." Raw C-style arrays can't be copy-constructed or assigned as a whole in C++98, so both the copy constructor and operator= loop over all 100 elements individually.

Dog.hpp composition through a private pointer

class Dog : public Animal {
private:
    Brain *brain;
public:
    Dog(void);
    Dog(const Dog &other);
    Dog &operator=(const Dog &other);
    virtual ~Dog();
    virtual void makeSound(void) const;
    Brain *getBrain(void) const;
};

Dog.cpp deep copy, both directions

Dog::Dog(void) {
    _type = "Dog";
    brain = new Brain();
    std::cout << "Dog default constructor called" << std::endl;
}
Dog::Dog(const Dog &other) : Animal(other) {
    brain = new Brain(*other.brain); // OWN allocation, contents copied — never share the pointer
    std::cout << "Dog copy constructor called" << std::endl;
}
Dog &Dog::operator=(const Dog &other) {
    std::cout << "Dog copy assignment operator called" << std::endl;
    Animal::operator=(other);
    *brain = *other.brain; // copy INTO existing Brain — Brain's own operator= does the real work
    return *this;
}
Dog::~Dog() {
    delete brain;
    std::cout << "Dog destructor called" << std::endl;
}
Fig 2 — exactly the rubric's own test: Dog tmp = basic; in a scope, checking for a double free at scope exit
Rubric's exact test, quoted

"Dog basic; { Dog tmp = basic; } — If the copy is shallow, tmp and basic will use the same Brain and the Brain will get deleted with tmp at the end of the scope." Worth running this specific pattern once, live, even though your own main.cpp proves the same thing a different way (comparing getBrain() addresses and independently modifying ideas).

Questions to expect

What would break if the copy constructor just did brain = other.brain?
Both objects would point at the same Brain. The first destructor to run would free it; the second destructor would then call delete on already-freed memory — a double free, undefined behavior.
Why does operator= use *brain = *other.brain instead of delete brain; brain = new Brain(*other.brain)?
Both are valid — the version used here reuses the existing allocation and copies into it via Brain's own operator=, avoiding an unnecessary delete/new pair. Either approach achieves a correct deep copy.
What happens without virtual on Animal's destructor, now that Dog owns a Brain?
delete on an Animal* pointing at a Dog would only call ~Animal(). ~Dog() — and its delete brain; line — would never run. The Brain becomes unreachable, a genuine memory leak, not just a missing print statement.
EvalHub rubric — quoted verbatim
"Cat and Dog have the required private Brain attribute. The Brain attribute should not be inside the Animal class."
Yes — Brain* brain is a private member of Dog and Cat individually; Animal has no knowledge of Brain at all.
"The copy [of] a Cat or a Dog should be a deep copy... The copy constructor should do a deep copy too."
Yes — both the copy constructor (new Brain(*other.brain)) and operator= (*brain = *other.brain) produce independent Brain contents, verified by comparing getBrain() addresses and modifying one without affecting the other.
"The destructors in Animal must be virtual."
Yes — virtual ~Animal(); confirmed necessary by the array-of-Animal* delete loop actually freeing every Brain (checked with valgrind, zero leaks).
"Check that the canonical form is really implemented (i.e. no empty copy assignment operators...). Nothing should be public for no reason."
Yes — brain is private on both Dog and Cat, only reachable via the public getBrain() accessor; all four OCF members present and functionally complete on every class involved.
ex02

Abstract class

One piece of syntax — = 0 — removes the one remaining awkward case: a plain Animal with no real sound of its own.

New concepts this exercise introduces
pure virtual function
virtual void makeSound(void) const = 0; — no implementation anywhere in the class, and the class becomes uninstantiable as a direct result.
propagation rule
Dog and Cat stay concrete without any changes, since they already fully implemented makeSound() back in ex00.

The pitch

"Everything from ex01 stays exactly the same — Brain, the deep copy, the array of base pointers. The only change is Animal::makeSound() becoming pure virtual, which makes Animal itself uninstantiable while Dog and Cat are completely unaffected, since they already implement it fully."

Walk the code

Animal.hpp the one-line change

// ex00/ex01 — has a body, class stays concrete
virtual void makeSound(void) const;

// ex02 — no body anywhere, class becomes abstract
virtual void makeSound(void) const = 0;

The corresponding implementation in Animal.cpp is deleted entirely — a pure virtual function has no body anywhere in the class that declares it. Dog.cpp and Cat.cpp need zero changes; both already provide their own complete makeSound().

main.cpp the required negative test

int main(void) {
    // Animal a; // uncomment to prove: compile error, cannot instantiate abstract class
    // "cannot declare variable 'a' to be of abstract type 'Animal'"
    ...
}

Left commented out on purpose — a concrete, one-line demonstration ready for evaluation. Uncomment, run make, show the real compiler error, recomment.

Fig 3 — one keyword change; Dog and Cat never notice the difference

Questions to expect

Why don't Dog and Cat need any changes for this exercise?
A class stays abstract only if a pure virtual function is left unimplemented somewhere in its chain. Dog::makeSound() and Cat::makeSound() already have real bodies from ex00, so they automatically remain concrete, instantiable classes.
What's the actual compile error, and what does it tell you?
Something like "cannot declare variable 'a' to be of abstract type 'Animal'" — it confirms the restriction is enforced at compile time, not something you have to remember to avoid by convention.
EvalHub rubric — quoted verbatim
"The Animal::makeSound is a pure virtual function. It should look like: virtual void makeSound() const = 0; The '= 0' part is mandatory."
Yes — present exactly as required in Animal.hpp, with no body anywhere in Animal.cpp.
"You should not be able to instantiate an Animal. Animal test; // should give you a compile error about the class being abstract"
Yes — verified live: uncommenting the test line and running make produces exactly this compile error.
"Class Cat and Dog are still present and work exactly like in ex01."
Yes — no changes to Dog.cpp or Cat.cpp; deep copy, virtual destructor chaining, and makeSound() all behave identically to ex01.
