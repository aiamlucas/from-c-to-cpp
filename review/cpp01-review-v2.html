ex00

BraiiiiiiinnnzzzZ

Zombie, newZombie & randomChump — the stack vs heap exercise.

New concepts this exercise introduces
new / delete
new allocates on the heap and runs the constructor; delete runs the destructor and frees the memory. Neither happens automatically.
automatic storage
A plain local object (no new) lives on the stack and is destroyed automatically the instant its scope ends.

The pitch

"This exercise is about deciding when an object should live on the stack versus the heap. I've got a Zombie class with a destructor that prints on death so the lifetime is actually visible, then two functions that create a zombie each way, and my main proves the difference by watching when each one dies."

Walk the code

Zombie.hpp header

#ifndef ZOMBIE_HPP
#define ZOMBIE_HPP
#include <iostream>
#include <string>

class Zombie {
private:
    std::string _name;

This class stores exactly one thing, the zombie's name, and it's private. Nothing outside the class can touch _name directly, that's the encapsulation habit from Module 00 showing up here even though this exercise doesn't explicitly ask for it.

public:
    Zombie(std::string name);
    ~Zombie();
    void announce(void);
};

Zombie *newZombie(std::string name);
void randomChump(std::string name);
#endif

The constructor takes the name, and the destructor and announce() are declared here too. The two free functions, newZombie and randomChump, are also declared in this header rather than only used inside main.cpp, because both .cpp files that implement them need to see this header, and anyone else including it gets the whole public interface in one place.

Zombie.cpp constructor, destructor, announce

Zombie::Zombie(std::string name) : _name(name) {}

This is the initialization list. It builds _name directly from the argument, instead of default-constructing it and assigning inside the body afterward. The visible result is the same either way here, but this is the correct habit to already have.

Zombie::~Zombie() { std::cout << _name << " destroyed" << std::endl; }

The subject requires the destructor to print for debugging, and this is what makes it possible to see. Without this line, an object's death would be completely invisible, you'd have no way to know when it actually happened.

void Zombie::announce(void) {
    std::cout << _name << ": BraiiiiiiinnnzzzZ..." << std::endl;
}

This matches the subject's exact output format: the name, a colon, then the message. No angle brackets appear in the real output, those were only in the subject to mark where the name goes.

newZombie.cpp heap

Zombie *newZombie(std::string name) { return new Zombie(name); }

One line, but it's the whole point of the exercise. new allocates the zombie on the heap, and the pointer it returns stays valid after this function ends. That's the only way to satisfy "returns it so you can use it outside the function scope," a stack-allocated zombie would already be destroyed by the time the caller got it back.

randomChump.cpp stack

void randomChump(std::string name) {
    Zombie z(name);
    z.announce();
}

z lives on the stack here. It's destroyed automatically the instant this function returns, so there's no delete anywhere in this function because none is needed.

main.cpp tests

{
    Zombie stackZombie("StackZombie");
    stackZombie.announce();
}
std::cout << "--- stack zombie is already gone ---" << std::endl;

Those bare braces force the zombie out of scope early, on purpose. Watch the output when this runs: "StackZombie destroyed" prints before "already gone", which is proof, not just a claim, that the destructor already ran by that point.

Zombie *heapZombie = newZombie("HeapZombie");
heapZombie->announce();
std::cout << "--- heap zombie still alive here ---" << std::endl;
delete heapZombie;

This zombie is on the heap, so it survives past the function that created it. It needs an explicit delete because nothing frees heap memory automatically, this pairs with the new inside newZombie: one new, one delete.

Questions to expect

Why is _name private instead of public?
Encapsulation. Nothing outside the class needs to rename a zombie directly, and keeping it private means if I ever wanted to validate or log a name change, there's exactly one place to add that.
Why does newZombie return a pointer instead of a Zombie by value?
Because the object has to outlive this function. A stack-allocated Zombie would be destroyed the moment the function returns, a pointer to heap memory is the only thing that survives past the creating scope.
What happens if you forget the delete on heapZombie?
Memory leak. The heap block becomes unreachable, nothing ever frees it, and the destructor never runs so you'd lose the debug print too. I can show that with valgrind if you want.
Why doesn't randomChump need a delete?
z is on the stack, its destructor fires automatically the moment the function's scope ends. Nothing to free manually because nothing was manually allocated.
Can you prove the stack zombie is actually destroyed when you say it is?
That's what the braces in main are for. Watch the output, the destroyed message prints before the next line runs, so the destructor already fired by then.
Important:
Can you justify the choice for randomChump — stack, or heap with an explicit delete. Which did you pick, and why?
Stack. randomChump's zombie only needs to exist for the duration of the function, it announces itself and then it's done, so there's no reason to hand it a longer lifetime than that. Heap would work too and the sheet accepts it, but it would mean remembering a delete for an object that never needed to outlive the function in the first place, extra responsibility with no benefit here.
Does the Zombie from newZombie get deleted correctly before the program ends?
Yes, delete heapZombie; runs in main before return 0;. I can point to the destructor's print in the output as proof it actually happened, not just that the line is present in the code.
ex01

Moar brainz!

zombieHorde — N objects, a single allocation.

New concepts this exercise introduces
new[] / delete[]
The array forms of new/delete. One call allocates a contiguous block of N objects; it must be freed with delete[], never plain delete.
default constructor
Array-new can only call a no-argument constructor on each element in C++98 — it can't forward arguments like a name.

The pitch

"This one's about a single allocation for N objects instead of N separate ones. Array-new can't forward constructor arguments in C++98, so I gave Zombie a default constructor and a setName, allocate the whole block in one new Zombie[N], then loop to name each one before handing back a pointer to the first."

Walk the code

Zombie.hpp header

class Zombie {
private:
    std::string _name;

Same private name as ex00, still the only thing this class stores.

public:
    Zombie();                       // default constructor - new Zombie[N]
    ~Zombie();                      // destructor
    void setName(const std::string &name); // alias to the caller's string, no copy made
    void announce(void);
};

Zombie *zombieHorde(int N, const std::string &name);
#endif

One constructor now, the default one, and it exists for exactly one reason: array-new in C++98 can only call a no-argument constructor for each element, it can't forward a name to any of them. setName is what lets a name get attached after the fact, once each zombie already exists. Both setName and zombieHorde take the name by const& now, so passing it around doesn't copy the string each time.

Zombie.cpp constructor, destructor, setName, announce

Zombie::Zombie() : _name("") {}

This is what makes new Zombie[N] possible at all. Every element in the array gets built with this constructor, starting with an empty name that setName immediately overwrites afterward.

Zombie::~Zombie() { std::cout << _name << " destroyed" << std::endl; }

Same debug print as ex00. This is what proves, in test 3, that every zombie in the block actually gets destroyed when the array is deleted, not just the first one.

void Zombie::setName(const std::string &name) { _name = name; }

The piece that makes the whole default-constructor route work. zombieHorde builds N nameless zombies, then calls this on each one to give it the actual name.

void Zombie::announce(void) {
    std::cout << _name << ": BraiiiiiiinnnzzzZ..." << std::endl;
}

Unchanged from ex00.

zombieHorde.cpp the single allocation

Zombie *horde = new Zombie[N]; // single allocation -> N zombies on the heap

This is the one allocation the exercise asks for. N default-constructed zombies, contiguous in memory, one pointer back to the first.

for (int i = 0; i < N; i++)
    horde[i].setName(name);
return horde; // returning a pointer to the first element

Since the constructor couldn't take the name directly, this loop gives every zombie its name right after allocation. horde already points at the first element, which is exactly what the function is supposed to return.

main.cpp tests

Zombie *single = zombieHorde(1, "Alone");
single[0].announce();
delete[] single;

Smallest case, N is 1, still goes through the same array-new path. delete[] matches the new[] inside zombieHorde.

Zombie *multiples = zombieHorde(5, "Chespirito");
for (int i = 0; i < 5; i++)
    multiples[i].announce();
delete[] multiples;

The real test of the exercise, calling announce() on every element of the horde, proving they're all valid and correctly named, not just the first one.

Zombie *ordered = zombieHorde(3, "Sunra");
delete[] ordered;

No announce() here on purpose. This test is only watching delete[] fire the destructor for all 3 zombies, proving the whole block gets cleaned up, not just element zero.

Questions to expect

Why does Zombie need a default constructor now, when it didn't in ex00?
Array-new can't forward constructor arguments in C++98. new Zombie[N] needs a no-argument constructor to build each element, so I added one plus setName to assign the real name afterward.
Why new Zombie[N] instead of looping new Zombie(name) N times?
The exercise specifically asks for a single allocation. new Zombie[N] gets one contiguous block and one pointer back, N separate calls would be N separate allocations and N pointers to track and free individually.
Why delete[] instead of plain delete?
It was allocated with new[]. delete[] runs the destructor on every element before freeing the block, plain delete on an array pointer only runs the first element's destructor and is undefined behavior.
Important:
Does the Zombie class have a default constructor, specifically?
Yes — Zombie(); with no parameters, that's a separate requirement from just "having a constructor," and it's the one array-new actually needs.
Are all the zombies deleted at the same time, in main?
Yes, each test's whole horde goes through one delete[] call on the pointer zombieHorde returned, not deleted element by element.
ex02

HI THIS IS BRAIN

Demystifying references: proving a reference has no address of its own.

New concepts this exercise introduces
reference (T&)
An alias for an existing variable, not a separate object — it has no address of its own, can't be null, and can never be rebound.
& in two roles
In a declaration, & means "this is a reference type." In an expression, it means "address-of," same as C.

The pitch

"This one's about showing that a reference isn't a separate object. stringPTR is a real variable that happens to store brain's address, but stringREF has no address of its own at all, asking for its address just gives you brain's, because they're the same thing."

Walk the code

main.cpp setup

std::string brain = "HI THIS IS BRAIN";
std::string *stringPTR = &brain;
std::string &stringREF = brain;

Three names, but only two objects. brain is the real string. stringPTR is a genuinely separate object that stores brain's address as its value. stringREF isn't a separate object at all, it's just another name for brain itself.

main.cpp addresses

std::cout << &brain << std::endl;
std::cout << stringPTR << std::endl;
std::cout << &stringREF << std::endl;

All three of these print the exact same address, and that's the actual point of the exercise. &brain is brain's address. stringPTR already holds that same address as its stored value. &stringREF also gives brain's address, because stringREF has no address of its own, asking for one just hands you brain's.

main.cpp values

std::cout << brain << std::endl;
std::cout << *stringPTR << std::endl;
std::cout << stringREF << std::endl;

Same reasoning, one level down. All three print the same value too: brain directly, *stringPTR by dereferencing to reach it, and stringREF because it already is brain, no dereference needed at all.

Questions to expect

Why do &brain, stringPTR, and &stringREF all print the same address?
stringPTR's stored value is brain's address by design, and stringREF isn't a separate object, so asking for its address just gives you brain's, there's nothing else to report.
What would print a different address here?
&stringPTR, since stringPTR is a real variable with its own storage. That's the one address in this exercise that wouldn't match the other three.
Why can't stringREF be pointed at a different string later?
A reference has to bind to something the moment it's declared, and that binding is permanent, there's no syntax to rebind an existing reference afterward.
Important:
Is the string's address displayed all three ways — through the variable, stringPTR, and stringREF?
Yes, that's the three cout lines back to back, all printing the same value for different reasons: brain directly gives its own address with &, stringPTR already stores it, and &stringREF resolves to it since a reference has no address of its own.
Is the content displayed all three ways too?
Yes, same pattern one level down: brain directly, *stringPTR dereferenced, and stringREF used as-is since it already is the string.
ex03

Unnecessary violence

HumanA always has a weapon, HumanB might not — the member type follows from that guarantee.

New concepts this exercise introduces
composition
A class holding another class as a member — a "has-a" relationship, as opposed to inheritance's "is-a."
reference vs pointer member
Reference for a relationship that's mandatory and fixed for life; pointer for one that can start absent (null) or be reassigned later.
initializer list requirement
A reference member has no legal default state, so it must be bound in the constructor's initializer list, never assigned in the body.

The pitch

"This one's about picking the right member type for a relationship. HumanA always has a weapon, so it holds a reference, HumanB might not, so it holds a pointer that can start null and get set later through setWeapon."

Walk the code

Weapon.hpp header

class Weapon {
private:
    std::string _type;
public:
    Weapon(const std::string &type);
    void setType(const std::string &type);
    const std::string &getType() const;
};

Same encapsulation shape as before, but getType() returns a const reference instead of a copy, so reading the type never copies the string, while const on the method itself promises it won't modify the Weapon.

HumanA.hpp header

class HumanA {
private:
    std::string _name;
    Weapon &_weapon;
public:
    HumanA(std::string name, Weapon &weapon);
    void attack() const;
};

_weapon is a reference, not a pointer. It has to be handed a real Weapon at construction, can never be null, and can never be pointed at a different Weapon later, that's exactly what "always armed" means.

HumanA.cpp constructor, attack

HumanA::HumanA(const std::string name, Weapon &weapon)
    : _name(name), _weapon(weapon) {}
void HumanA::attack() const {
    std::cout << _name << " attacks with their " << _weapon.getType()
              << std::endl;
}

The reference gets bound in the initialization list, that's the only place it's allowed to happen. Because _weapon is an alias for the exact Weapon passed in, if that Weapon's type changes later, attack() sees the change too, without HumanA doing anything.

HumanB.hpp header

class HumanB {
private:
    std::string _name;
    Weapon *_weapon;
public:
    HumanB(const std::string &name);
    void attack() const;
    void setWeapon(Weapon &weapon);
};

_weapon is a pointer here, on purpose. It can start out null, and setWeapon can point it at a Weapon after construction, neither of those is possible with a reference.

HumanB.cpp constructor, setWeapon, attack

HumanB::HumanB(const std::string &name) : _name(name), _weapon(NULL) {}
void HumanB::setWeapon(Weapon &weapon) { _weapon = &weapon; }
void HumanB::attack() const {
    if (_weapon)
        std::cout << _name << " attacks with their " << _weapon->getType()
                  << std::endl;
}

Jim starts with _weapon set to NULL. setWeapon stores the address of whatever Weapon it's given. attack() checks _weapon before dereferencing it, that check exists specifically because this pointer might still be null.

main.cpp tests

Weapon club("crude spiked club");
HumanA bob("Bob", club);
bob.attack();
club.setType("some other type of club");
bob.attack();

Bob's reference is bound to this exact club. Changing club's type after construction changes what bob reports too, since there's only ever one Weapon here.

Weapon club("crude spiked club");
HumanB jim("Jim");
jim.setWeapon(club);
jim.attack();
club.setType("some other type of club");
jim.attack();

Jim starts unarmed, gets armed via setWeapon, and then sees the same type change club does afterward, same underlying reasoning as bob, just wired through a pointer instead of a reference.

Questions to expect

Why does HumanA take its Weapon in the constructor, but HumanB doesn't?
HumanA's _weapon is a reference, and a reference has to be bound the moment the object is constructed, there's no way to set it later. HumanB's pointer can be left null and assigned afterward.
What happens if you call jim.attack() before setWeapon?
Nothing prints. _weapon is still NULL at that point, and attack() checks for that before trying to use it, so it just skips the output instead of crashing.
Why does getType() return a const reference instead of a plain std::string?
To avoid copying the string on every call, while the const still stops the caller from modifying the Weapon's actual type through what's returned.
Important:
Could HumanA have used a pointer instead of a reference? Would that still pass?
Reference is a more precise choice. HumanA is guaranteed to always have a Weapon from construction onward and never swap it, a reference enforces that at compile time, a pointer would only enforce it by convention, nothing would stop me from accidentally reassigning or nulling it.
Why must HumanB use a pointer, not a reference?
HumanB's Weapon isn't set at construction, it can be NULL, and setWeapon can assign it after the fact. A reference can't be null and can't be rebound, so it's not an option here, this is the one case the sheet is strict about.
ex04

Sed is for losers

Find and substr build a replace-all, since std::string::replace is off-limits.

New concepts this exercise introduces
ifstream / ofstream
C++'s RAII file streams — the file opens in the constructor and closes automatically in the destructor, no manual open/close bookkeeping.
find() / substr() / npos
Locate a substring, then cut around it to rebuild the string piece by piece; npos is the sentinel meaning "no match found."

The pitch

"This one opens a file, walks it line by line, and rebuilds every line with every occurrence of s1 swapped for s2, using find and substr since replace() isn't allowed."

Walk the code

Replacer.hpp header

class Replacer {
private:
    std::string _fileName;
    std::string _s1;
    std::string _s2;
    std::string _replaceLine(const std::string &line);
public:
    Replacer(const std::string &fileName, const std::string &s1,
             const std::string &s2);
    ~Replacer();
    void run();
};

The three strings from the command line are stored once at construction. _replaceLine is private, it's an internal helper run() uses, not something the outside world needs to call directly.

Replacer.cpp constructor

Replacer::Replacer(const std::string &fileName, const std::string &s1,
                   const std::string &s2)
    : _fileName(fileName), _s1(s1), _s2(s2) {}

Straightforward initialization list, all three members copied in directly from the constructor's arguments.

Replacer.cpp _replaceLine

std::string Replacer::_replaceLine(const std::string &line) {
    std::string result;
    size_t pos = 0;
    size_t found;
    while ((found = line.find(_s1, pos)) != std::string::npos) {
        result += line.substr(pos, found - pos);
        result += _s2;
        pos = found + _s1.length();
    }
    result += line.substr(pos);
    return result;
}

find() locates the next occurrence of s1 starting from pos. Everything between the last position and that match gets copied as-is, then s2 gets appended instead of the match itself, and pos jumps past it. The loop keeps going until find() can't find any more, and whatever's left after the last match gets appended at the end.

Replacer.cpp run

void Replacer::run() {
    std::string outName = _fileName + ".replace";
    std::ifstream inFile(_fileName.c_str());
    if (!inFile.is_open()) { std::cerr << "Could not open file\n"; return; }

    std::ofstream outFile(outName.c_str());
    if (!outFile.is_open()) { std::cerr << "Could not create output file\n"; return; }

    std::string line;
    while (std::getline(inFile, line))
        outFile << _replaceLine(line) << "\n";
    inFile.close();
    outFile.close();
}

.c_str() is required here because C++98's ifstream/ofstream constructors only accept const char*, not std::string directly. Both files get checked with is_open() before use. Each line gets read, replaced, and written out with its own newline.

main.cpp the empty-s1 guard

if (s1.empty()) {
    std::cerr << "s1 cannot be empty\n";
    return 1;
}

This matters more than it looks. If s1 were empty, find() would match at every position and the replace loop would never advance, an infinite loop. Catching it here before Replacer ever runs avoids that entirely.

Questions to expect

What happens if s1 doesn't appear anywhere in the file?
find() returns npos immediately on every line, the while loop in _replaceLine never runs, and each line comes back through the tail-append line unchanged.
Why check s1.empty() in main instead of inside Replacer?
An empty s1 would make find() match at every position with zero length, so pos never advances, that's an infinite loop. Catching it in main before a Replacer is ever created is the simplest place to stop it.
Could a match that spans two lines get missed?
Yes, technically, since this reads and replaces one line at a time. In practice s1 comes from a command-line argument, so it can't realistically contain an actual embedded newline character, which is why this wasn't worth solving for here.
Important:
Have you tested a file that doesn't exist, one with changed permissions, and an empty file?
Missing file: is_open() catches it, clean error message, no crash. Empty file: getline just never succeeds, the loop body never runs, and an empty .replace file is produced, which is correct behavior, not a bug. Permissions I can demo live with chmod to show is_open() still catches an unreadable file the same way.
Is the implementation done with std::string functions, not character by character?
Yes, the whole replace logic is find() plus substr(), no manual char-by-char scanning. That's the actual point being checked here, not just that it works, but that it works the C++ way.
ex05

Harl 2.0

Dispatch through an array of pointers to member functions, no if/else chain.

New concepts this exercise introduces
pointer to member function
A function pointer scoped to a class. It can't be called alone — it needs an object supplied alongside it via .* or ->*.
dispatch table
An array of these pointers, indexed the same way as a parallel array of names, used as a lookup instead of branching logic.

The pitch

"Harl always says the same four things, so instead of branching on the level string with if/else, I built a small lookup: an array of pointers to member functions, indexed the same way as an array of level names."

Walk the code

Harl.hpp header

class Harl {
private:
    void debug(void);
    void info(void);
    void warning(void);
    void error(void);
public:
    void complain(std::string level);
};

The four rants are private, complain() is the only public entry point, callers pick a level, not a specific method.

Harl.cpp complain

void Harl::complain(std::string level) {
    typedef void (Harl::*HarlFunc)(void);
    HarlFunc funcs[4] = {&Harl::debug, &Harl::info, &Harl::warning, &Harl::error};
    std::string levels[4] = {"DEBUG", "INFO", "WARNING", "ERROR"};
    for (int i = 0; i < 4; i++) {
        if (levels[i] == level) {
            (this->*funcs[i])();
            return;
        }
    }
}

The typedef just gives the pointer-to-member-function type a readable name. funcs and levels are parallel arrays, same index means "this name goes with this function." The loop finds which index matches the level string, then calls that function on this, that's the whole dispatch, no if/else chain at all.

Questions to expect

What does &Harl::debug actually mean, why not just &debug?
A member function needs a class to be scoped to, that's what makes it a pointer-to-member instead of an ordinary function pointer. Even from inside the class, you have to qualify it with Harl::.
What does (this->*funcs[i])() do?
It binds the function pointer in funcs[i] to the current object via this, then calls it. Without an object, a pointer to a member function can't actually be called, it needs something to run against.
What happens if level doesn't match any of the four strings?
The loop finishes without ever calling anything, complain() just returns silently. That's fine for this exercise, ex06 is the one that adds a fallback for unmatched input.
Important:
The sheet says any implementation is valid as long as it's not an ugly if/elseif/else, and matching strings to function pointers is only the "ideal" approach. Why did you pick this one anyway?
Because it's what the subject is actually testing — pointers to member functions specifically, not just "avoid if/else somehow." A switch on a hashed string or a map, if STL were allowed here, would also dodge if/else without touching the actual concept the exercise wants demonstrated.
The sheet says you could display your own messages instead of the subject's examples. Did you, and why?
I used the subject's own examples. Either is marked valid, I just didn't see a reason to write new ones when the exercise isn't really about the content of the complaints, it's about the dispatch mechanism getting to them.
ex06 optional

Harl filter

Same four rants, now filtered by level-and-above using a switch with fallthrough.

New concepts this exercise introduces
switch / case / default
Jumps to the matching case label and keeps executing forward through every following case until it hits a break.
fallthrough
Deliberately omitting break so execution continues into the next case — here, that's what makes "this level and above" work.

The pitch

"harlFilter takes one level and prints every message at that level or above. The trick is a switch with no break between cases on purpose, matching WARNING falls straight through into ERROR, which is exactly the behavior the subject's example shows."

Walk the code

Harl.cpp debug, info, warning, error

void Harl::debug(void) {
    std::cout << "[ DEBUG ]" << std::endl;
    std::cout << "I love having extra bacon..." << std::endl;
}
// info(), warning(), error() follow the same shape

Each function now prints its own level tag before the message, that's what produces the [ WARNING ] style headers the subject's example output shows.

Harl.cpp complain — find the index

void Harl::complain(std::string level) {
    std::string levels[4] = {"DEBUG", "INFO", "WARNING", "ERROR"};
    int index = -1;
    for (int i = 0; i < 4; i++) {
        if (levels[i] == level) {
            index = i;
            break;
        }
    }

switch only works on integral types, not std::string, so the level string has to be translated to an index first. index stays -1 if nothing matches, that's what routes into default below.

Harl.cpp complain — the switch itself

    switch (index) {
        case 0: debug();    // no break, falls through on purpose
        case 1: info();
        case 2: warning();
        case 3: error();
            break;
        default:
            std::cout << "[ Probably complaining about insignificant problems ]"
                      << std::endl;
    }
}

This is the whole exercise in one block. Match at case 2 (WARNING) and execution runs warning(), then falls into case 3 and runs error() too, only stopping at that final break. Match at case 0 (DEBUG) and all four run in order. default catches index == -1, an unrecognized level.

main.cpp entry point

if (argc != 2) {
    std::cerr << "Usage: ./harlFilter <level>\n";
    return 1;
}
std::string complainAbout = argv[1];
harl.complain(complainAbout);

One argument in, straight into complain(). The executable name matches the subject's requirement, harlFilter, and the whole level-and-above behavior lives entirely inside the switch, not in main.

Questions to expect

Why no break between the cases?
That's the actual mechanism the subject wants. Without a break, matching one case keeps executing forward through every case below it, which is exactly "this level and above" without writing that logic out manually.
Why does GCC complain about implicit fallthrough here, and how did you handle it?
-Werror turns the implicit-fallthrough warning into a hard error, since accidentally missing a break is a common real bug. I added __attribute__((fallthrough)) at each intentional fallthrough point to tell the compiler this one's deliberate.
What happens with an argument that isn't one of the four levels?
index stays -1, none of the case labels match it, so switch jumps straight to default and prints the insignificant-problems line, same as the subject's own example.
Important:
Is this implemented with a switch statement and a default case, and no if/elseif/else?
Yes. The only if in the file is the one-line argc check in main, the actual level-based logic is entirely the switch block, with default handling anything that doesn't match.
Does harlFilter WARNING correctly print both WARNING and ERROR, in order?
Yes, that's the fallthrough from case 2 into case 3, I can run it live: WARNING's tag and message print first, then ERROR's, nothing printed for DEBUG or INFO.
