Sheet 00

Two kinds of polymorphism, and why they're not the same thing

Operator overloading already taught you one kind. This is the other kind — and the difference is entirely about when the decision of "which function actually runs" gets made.

Polymorphism just means "many forms" — one name, several behaviors depending on context. You've already met one flavor of it: overloading operator+, operator<<, and friends on a class like Fixed. That's called ad-hoc polymorphism — the compiler decides which version of + to call purely by looking at the types involved, entirely at compile time, before the program ever runs.

This document is about the other kind: subtype polymorphism, also called runtime polymorphism. The idea: a single function call, written once, can run different code depending on what the object actually is underneath — decided while the program is running, not while it's compiling.

Ad-hoc polymorphismSubtype polymorphism
Decided whencompile timeruntime
Decided bythe types of the operandsthe actual object's type, however it's referenced
Mechanismfunction overloading (same name, different signatures)virtual functions, resolved through a hidden lookup table
Example already seenFixed::operator+, operator<<a Shape* that could point at a Circle or a Rectangle

You've actually already brushed up against the boundary of this topic without the tool that makes it work: redefining attack() in a derived class, where calling it through a base-class pointer still ran the base's version. That was name hiding, resolved statically. Subtype polymorphism is the deliberate mechanism that flips that resolution to runtime — and it needs exactly one new keyword to do it.

The running example for this document

A Shape base class, and three concrete shapes that specialize it: Circle, Rectangle, Triangle. Each needs to compute its own area() completely differently — there's no shared formula to fall back on — which makes it a clean, honest example of when you actually need runtime polymorphism rather than reaching for it out of habit.

Sheet 01

virtual, and how dynamic dispatch actually works

One keyword flips function resolution from "decided by the pointer's type" to "decided by the object's real type" — and it costs a small, well-understood amount of indirection to do it.

Recall the default behavior of ordinary member functions: called through a base-class pointer, they resolve by the pointer's declared type, not the object's real one. Marking a function virtual in the base class changes that rule entirely for that function, and every override of it in every derived class.

class Shape {
public:
    virtual double area() const { return 0.0; } // virtual — resolved at runtime
    virtual ~Shape() {}                     // see Sheet 03 for why this matters
};

class Circle : public Shape {
    double _radius;
public:
    Circle(double r) : _radius(r) {}
    double area() const { return 3.14159 * _radius * _radius; } // overrides Shape's
};

class Rectangle : public Shape {
    double _w, _h;
public:
    Rectangle(double w, double h) : _w(w), _h(h) {}
    double area() const { return _w * _h; }
};
Shape *s = new Circle(3.0);
std::cout << s->area(); // prints ~28.27 — Circle's area(), not Shape's
                          // even though s is declared as Shape*

Compare this directly against the static-binding case from before: without virtual, this exact code would call Shape::area() and print 0.0. With it, the call correctly reaches Circle::area(). Nothing about the call syntax changed — only the one keyword in the base class declaration.

Fig. 01 — the fix, contrasted directly with the static-binding failure from the inheritance reference

The mechanism: a hidden pointer, and a table of function addresses

This isn't magic — it's a small, deliberate piece of extra bookkeeping the compiler inserts. The instant a class declares (or inherits) even one virtual function, every object of that class secretly gains one extra hidden member: a vptr (virtual table pointer), pointing at a per-class table of function addresses called a vtable.

Fig. 02 — how s->area() actually resolves at runtime, one indirection at a time

This is why it works regardless of which pointer type you're holding: the vptr belongs to the object, set once at construction to point at its own class's vtable, and it never changes for that object's lifetime. A Shape* pointing at a Circle still follows that same vptr to Circle's vtable — the pointer's declared type never enters the lookup at all.

The cost, briefly

Every virtual call costs one extra pointer dereference compared to a plain function call — real but small, and the reason C++ makes you opt in with virtual rather than making every function work this way by default. A class with no virtual functions at all carries no vptr and pays nothing.

Sheet 02

Pure virtual functions, and what makes a class abstract

A base class that has no sensible default implementation for a function can say so explicitly — and the moment it does, that class can no longer be built on its own.

Shape::area() from Sheet 01 has a real problem: what should the base class's own area() actually return? There's no meaningful "generic shape's area" — it only makes sense once you know whether you're looking at a circle or a rectangle. Returning 0.0 as a placeholder is a lie waiting to cause a bug if someone forgets to override it.

C++ lets you say this directly: pure virtual function, marked with = 0 instead of a body.

class Shape {
public:
    virtual double area() const = 0; // pure virtual — no body, no default
    virtual ~Shape() {}
};

The moment a class has even one pure virtual function, it becomes an abstract class. The consequence is immediate and enforced by the compiler: you can no longer create a plain Shape object.

Shape s;                    // COMPILE ERROR — cannot instantiate abstract class
Shape *ptr = new Shape();  // COMPILE ERROR, same reason

Shape *ptr = new Circle(3.0); // fine — Circle is concrete
Fig. 03 — Shape can never be built directly; only fully-implemented derived classes can

The rule that propagates: a derived class must implement every pure virtual, or stay abstract itself

If Triangle inherits from Shape but never provides a body for area(), Triangle is also abstract — the pure-virtual-ness doesn't go away just because you inherited from the class that declared it. You can build multi-level hierarchies where an intermediate abstract class implements some pure virtuals but not others, staying partially abstract, but only a class where every pure virtual has a real body anywhere in its inheritance chain becomes concrete and instantiable.

Class has...Can you write ClassName obj; ?
Zero pure virtual functionsYes — ordinary concrete class
One or more pure virtual, none implementedNo — abstract
Some pure virtual implemented, some notNo — still abstract
Every pure virtual implemented somewhere in the chainYes — concrete
An abstract class can still have real code

Shape isn't limited to pure virtual functions only — it can have ordinary data members, a constructor, and fully-implemented ordinary member functions alongside its pure virtual ones. Abstract just means "at least one function has no body yet," not "nothing in this class works." Shape could, for example, have a concrete describe() function that every derived shape inherits unchanged, sitting right next to the pure virtual area() that each one must supply itself.

Why bother, instead of just returning 0.0 and trusting yourself to override it?

The pure virtual version turns a discipline problem into a compile error. If you add a new shape, say Pentagon, and forget to implement area(), the plain-virtual version would silently compile and hand you back 0.0 at runtime — a bug that might not surface until much later, in production, on real data. The pure virtual version refuses to compile at all until Pentagon::area() exists. The mistake becomes impossible to ship, not just unlikely.

Sheet 03

The virtual destructor problem

One specific, easy-to-miss bug: deleting a derived object through a base pointer, when the base's destructor isn't virtual, leaks memory silently — no warning, no crash, just a quiet loss.

Every class in this document's examples has included virtual ~Shape() {} from the very first code block. Here's exactly why that line is not optional.

class Circle : public Shape {
    double *_cachedPoints; // suppose Circle allocates something on the heap
public:
    Circle(double r) : _radius(r), _cachedPoints(new double[360]) {}
    ~Circle() { delete[] _cachedPoints; } // Circle's own cleanup
};
Shape *s = new Circle(3.0);
delete s; // what actually gets destroyed here?
Fig. 04 — without virtual, delete s only ever calls Shape's destructor, no matter what s really points to

Without virtual on the destructor, delete s; resolves exactly like any other non-virtual member function call: by s's declared type, Shape*. Only ~Shape() runs. Circle's destructor — the one that would have freed _cachedPoints — never executes at all. The memory is gone, unreachable, leaked, with no error and no crash to signal anything went wrong.

The rule, stated simply

Any class you intend to delete through a base-class pointer — which, in practice, means any class with at least one other virtual function — needs a virtual destructor. This is common enough advice that it has a name: "if a class has any virtual functions, it should have a virtual destructor." The reverse isn't automatically true — a class with no virtual functions at all, never meant to be a polymorphic base, doesn't need one — but the moment polymorphism enters the picture, this stops being optional.

Note the destructor doesn't need = 0 to make Shape abstract — a pure virtual destructor is legal and occasionally used, but it still needs an actual body defined somewhere, since destructor chaining always calls every level regardless. In practice, area() alone being pure virtual is already enough to make Shape abstract; the destructor's job here is purely about correct cleanup, not about abstractness.

Sheet 04

Interfaces in C++ — a pattern, not a keyword

Unlike Java or C#, C++ has no interface keyword. The same idea is built entirely out of tools you already have: an abstract class with nothing but pure virtual functions.

An interface, as a concept, is a pure contract: "any class implementing me promises to provide these functions," with zero shared implementation and zero shared data. C++ doesn't need new syntax for this — a class that is entirely pure virtual, with no data members and no function bodies at all, already behaves exactly like one.

class Drawable {
public:
    virtual void draw() const = 0;   // pure virtual, no data, no body
    virtual ~Drawable() {}          // still needs a real destructor body
};

Nothing here stores anything or computes anything. Drawable is purely a promise: "if you inherit from me, you must provide a draw()." That's the entire interface pattern in C++ — no special syntax, just an abstract class disciplined enough to carry no state of its own.

Implementing more than one "interface" at once

Because Drawable carries no data at all, a class can inherit from it and from Shape simultaneously — genuine multiple inheritance, but without the diamond-problem data-duplication risk from the inheritance reference, since there's no data here to duplicate in the first place.

class Circle : public Shape, public Drawable {
    double _radius;
public:
    Circle(double r) : _radius(r) {}
    double area() const { return 3.14159 * _radius * _radius; } // satisfies Shape
    void draw() const { std::cout << "○ radius " << _radius; }         // satisfies Drawable
};
Fig. 05 — Circle satisfies two separate contracts at once, each checked independently by the compiler

Abstract class vs interface-style class: the actual difference

Abstract class (Shape)Interface-style class (Drawable)

This is exactly why interface-style classes in C++ are often named starting with a capital I or ending in -able by convention — IDrawable, Drawable, Comparable — purely as a signal to other developers, since the compiler enforces no such naming and treats an interface-style class identically to any other abstract class under the hood.

Sheet 05

Polymorphic collections — the actual payoff

Everything so far has been mechanism. This is the reason any of it is worth building: one loop, one function call, correct behavior for every different shape inside it.

Without polymorphism, printing the total area of a mixed collection of shapes would need a type check and a branch for every single kind of shape — and every time you add a new shape, you'd have to remember to update that branch too, everywhere it appears in your codebase.

// the version you'd be stuck with, without virtual functions
double totalArea = 0;
for (size_t i = 0; i < shapes.size(); i++) {
    if (shapes[i]->getType() == CIRCLE)
        totalArea += 3.14159 * static_cast<Circle*>(shapes[i])->getRadius() * ...;
    else if (shapes[i]->getType() == RECTANGLE)
        totalArea += static_cast<Rectangle*>(shapes[i])->getWidth() * ...;
    // ...one more branch for every shape that will EVER exist, forever
}
// with virtual functions — this is the entire loop, forever, no matter how many shapes exist
double totalArea = 0;
for (size_t i = 0; i < shapes.size(); i++)
    totalArea += shapes[i]->area(); // correct area, whatever the real type is
Fig. 06 — one array of base pointers, three different real objects, one call site that's correct for all of them

This is the actual argument for the whole mechanism, not just a syntax curiosity: adding a fourth shape, Pentagon, requires writing class Pentagon : public Shape and implementing its area() — and every single piece of existing code that loops over vector<Shape*>, anywhere in the program, automatically handles it correctly, with zero changes. The alternative — a type-checking branch for every kind of shape — would need updating in every single one of those places, every time.

Cleanup still matters here

If shapes holds pointers built with new, each one still needs an explicit delete — polymorphism doesn't change ownership or memory management rules from Module 01. And this is precisely why the virtual destructor from Sheet 03 is not optional in a setup like this: delete shapes[i]; runs through exactly the same base-pointer path that made the destructor's virtual-ness matter in the first place. Skip it here, and every single shape in the collection leaks whatever its own destructor was supposed to clean up.
