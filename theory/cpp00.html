Sheet 00

The big picture

Module 00 isn't really about syntax. It's the moment data stops being a buffer you manage by hand and starts being an object that manages itself.

In C, "an account" would be a struct plus a pile of free functions that all take a pointer to it and hope nobody calls them out of order. C++ lets the data and the functions that operate on it live in one place, with rules the compiler enforces about who's allowed to touch what. Everything in this module — std::string, classes, const, static — is building toward that one shift.

Rules worth keeping in view

  • No STL yet — no containers, no <algorithm>. That's Module 08/09. Fixed-size C-arrays and hand-written loops are the tool for now.
  • No printf(), *alloc(), free() — the C++ standard library has a replacement for all of them; reaching for the C version is an instant 0, not a style deduction.
  • Header/implementation split is enforced — a function body in a .hpp (outside templates) is worth 0 to the exercise, not just bad style.
  • Include guards are mandatory — every header must be safely includable on its own, with no double-inclusion crashes.
  • No using namespace std; — every standard-library name gets its std:: prefix, explicitly, every time.
Goodbye Norminette

No enforced style here — but "code your peer evaluator can't follow is code they can't grade" is doing the same job Norminette used to. Consistent naming and a header/implementation split people can actually navigate matters more than it did in C.

Sheet 01 · Exercise 00 — Megaphone

Streams and std::string

A tiny exercise carrying two ideas that show up in every file from here on: stream objects, and strings that manage their own memory.

cout / cin are objects, not syntax

std::cout << x is an overloaded operator call, not special syntax — << inserts into the stream and returns a reference to that same stream, which is exactly why cout << a << b chains. std::endl writes a newline and flushes the output buffer; "\n" only does the first. Default to "\n", reach for endl only when the flush itself matters — the difference is invisible in a one-shot program but real in a loop that runs thousands of times.

std::string vs a C string

A C string is just a char* — you own the buffer, you track the length, and one off-by-one puts you past the end of it. std::string is a real object: it allocates its own memory in its constructor, frees it in its destructor, and knows its own length. That's the pattern called RAII — resource acquisition is initialization — and it's the reason += and .length() replace strcat and manual buffer math for the rest of the curriculum.

Casts, and one real gotcha

A C-style cast like (int)x silently picks whichever of static_cast, const_cast, or reinterpret_cast the context allows — C++ gives you four named casts that each do one specific thing and fail to compile if misused. static_cast<int>(x) is more typing for the same result, but it's a reflex worth building now.

Real bug, not a style note

std::toupper takes a value representable as unsigned char or EOF. Passing it a plain (likely signed) char that happens to hold a negative byte value is undefined behavior, not just untidy — the fix is std::toupper(static_cast<unsigned char>(c)). It's an easy one to never notice on your own machine and worth internalizing now, since it'll keep coming up anywhere character-classification functions touch raw char values.

Sheet 02 · Exercise 01 — My Awesome PhoneBook

Classes, encapsulation & constructors

The exercise where "anything used inside the class is private, anything used outside is public" stops being a slogan and becomes a design decision you make for every member.

Encapsulation

A class's private data can only be touched through the public interface it chooses to expose. That's not bureaucracy, it means the class can change how it stores something internally without breaking anyone who only ever called its public methods, and it means invariants (like "no field can be empty") can actually be enforced in one place instead of trusted to every call site.

Constructors & the initialization list

A constructor runs automatically the moment an object exists. The part after the colon, : _count(0), is the member initialization list and it's not interchangeable with assigning inside the constructor body, even when the visible result looks the same.

Fig. 03 — one step vs two, for the exact same value
Why this stops being cosmetic

For a plain int the compiler optimizes the difference away. It stops being optional the moment a member is const, a reference, or an object of a class with no default constructor. Those can only be set once, at construction, so assignment in the body won't compile at all. Building the init-list habit now means you're not relearning it under pressure later.

const-correctness on getters

std::string getFirstName() const; — the trailing const is a compiler-enforced promise that calling this method cannot modify the object. Reading a contact's name shouldn't be able to mutate the contact; marking every read-only method const is what lets the compiler catch it if it ever accidentally could.

What the compiler writes for you

Declare no constructors, destructor, or assignment operator yourself, and the compiler silently generates a default constructor, copy constructor, copy assignment operator, and destructor. For a class like Contact whose only members are std::strings, the generated copy constructor — a plain memberwise copy — is completely correct, which is why passing a Contact by value into PhoneBook::addContact just works with no code written for it.

Where this stops being safe

That free memberwise copy only stays correct as long as nothing in the class owns raw allocated memory. The moment a class holds a pointer from new, the compiler-generated copy constructor copies the pointer, not what it points to — two objects end up pointing at the same memory, and one destructor eventually frees it out from under the other. That's exactly why the Orthodox Canonical Form becomes mandatory starting Module 02. Not relevant yet with plain std::string members — just worth knowing why the rule exists before you meet it.

iomanip, briefly

std::setw(10) fixes the field width for the next thing printed, std::right right-aligns it — both live in <iomanip> and both need to be re-applied before each field, since setw only affects the single next insertion. Truncation to "9 characters + a dot" is manual string logic (.substr()), not something iomanip does for you.

Sheet 03 · Exercise 02 — The Job Of Your Dreams (optional)

Static members & reconstructing from a spec

Recreating Account.cpp from a header and a log file is really an exercise in two things: static state, and disciplined output-matching.

static: one copy, shared by every instance

A normal member variable is per-object — each Account has its own _amount. A static member variable belongs to the class itself: there's exactly one copy, shared across every instance, which is exactly the shape you need for something like "how many accounts exist in total" or "total amount currently deposited across the whole bank."

Fig. 04 — per-instance data vs one shared class-level counter

A static member function follows from this: it can be called without any instance (Account::displayAccountsInfos() rather than through an object), and correspondingly it can only touch other static data — it has no instance to work with, so there's no _amount for it to see.

Instance data

Belongs to one object. _amount, _nbDeposits — each Account has its own. Needs an object to exist at all.

Class data

Belongs to the class as a whole. _nbAccounts, _totalAmount — one copy, shared, updated from every constructor/destructor/deposit/withdraw call regardless of which instance triggered it.

Reconstructing behavior from a log

This exercise isn't testing whether you can invent an Account class — the header is already given. It's testing whether you can read a specification (the header's declared interface) and a record of expected behavior (the log) and produce an implementation that matches both exactly. A few habits that generalize well beyond this one exercise:

  • Match structure before matching values — get the shape of each printed line right first, then worry about getting the exact numbers right.
  • Timestamps will differ, and that's expected — the log was generated before you existed as a student; don't chase matching the literal timestamp, only its format.
  • Destructor order isn't guaranteed — the subject calls this out explicitly. If your accounts are destroyed in a different order than the reference log, that alone isn't a sign something's wrong.
  • Test incrementally — run tests.cpp against small pieces of behavior as you implement them, rather than writing the whole class and debugging against the full log at the end.
Not mandatory, still worth doing

The subject explicitly says finishing this exercise isn't required to pass the module. It's still the best static-members practice in Module 00 — worth attempting even under time pressure, since this exact class-level-vs-instance-level distinction reappears constantly from here on.
