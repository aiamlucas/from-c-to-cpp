Sheet 00

The big picture

Module 03 taught a derived class to physically contain its base. Module 04 asks the harder question: once you're holding an object only through its base type, which function actually runs when you call one?

You already met one flavor of polymorphism back in Module 02, overloading operator+, operator<< on Fixed. That's ad-hoc polymorphism — the compiler decides which version to call purely from the types involved, entirely at compile time. This module is about the other kind: subtype polymorphism, where the exact same call, written once, runs different code depending on what the object actually is, decided while the program is running.

Ad-hoc polymorphism (Module 02)Subtype polymorphism (this module)
Decided whencompile timeruntime
Decided bythe types of the operandsthe actual object's type, however it's referenced

Already seenFixed::operator+ClapTrap::attack() hidden, not overridden, in Module 03

The three exercises build on each other in a specific order: ex00 proves virtual actually changes which function runs, ex01 gives a class something real to lose if that mechanism fails (a heap-owned resource), and ex02 removes the fallback entirely — the base class stops being buildable on its own at all.

The running example

Animal, specialized into Dog and Cat. Both need a genuinely different makeSound() — there's no shared, sensible default — which is exactly the shape that makes runtime polymorphism the right tool rather than a syntax preference.

Sheet 01 · Exercise 00 — Polymorphism

Animal, Dog, Cat — making virtual actually matter

Cats don't bark. The whole exercise is built around one line of output telling you whether your class hierarchy actually knows that.

Animal holds one protected attribute, _type, set by each derived class's own constructor. Nothing about that part is new after Module 03. What's new is makeSound(), and specifically what happens to it once you call it through a pointer whose declared type doesn't match the real object underneath.

class Animal {
protected:
    std::string _type;
public:
    std::string getType(void) const;
    virtual void makeSound(void) const; // the entire exercise hinges on this keyword
};
Fig. 01 — the subject's own test, and why it needs virtual specifically

Calling makeSound() directly on a named Dog or Cat variable proves nothing — the compiler already knows the exact type at compile time in that case, so the call resolves correctly whether or not the function is virtual. The real test only exists the moment the declared type and the real type genuinely diverge — an Animal* that actually points at a Dog.

WrongAnimal / WrongCat: proving it by building the failure on purpose

The subject asks for a second, structurally identical pair, differing in exactly one place: WrongAnimal::makeSound() is deliberately not virtual. Same shape, same inheritance, same test — but the outcome is now the broken one, on purpose.

Animal / Dog / CatWrongAnimal / WrongCat
makeSound() virtual?YesNo

Why the destructor line matters more than the sound line

A wrong sound is cosmetically wrong but harmless. A skipped destructor is the dangerous half of this exercise: if WrongCat owned anything on the heap, deleting it through a WrongAnimal* would leak that memory silently, with zero indication anything went wrong. Ex00's classes own nothing yet, so nothing actually leaks here — the missing destructor print statement is the only visible symptom. Ex01 changes that.

Sheet 02 · Exercise 01 — I don't want to set the world on fire

Brain, and the difference between copying a value and copying an owner

Dog and Cat now own something on the heap. Every shortcut that was merely stylistic in ex00 becomes load-bearing here.

Brain has no relationship to Animal at all — it doesn't inherit from anything, and nothing inherits from it. Dog and Cat each hold a Brain* as a private member. This is composition (has-a), the exact relationship from Module 03's overview sheet, sitting right alongside the is-a relationship Dog : public Animal already gives them.

Fig. 02 — two relationships, one class: is-a Animal, has-a Brain

Shallow copy is the exact bug Orthodox Canonical Form exists to prevent

This connects directly back to Module 02: for a class holding only plain values, the compiler's automatic copy constructor is harmless. The moment a class owns a heap pointer, that automatic version just copies the address, not the data — two objects end up sharing one Brain, and the first destructor to run frees memory the second one still believes it owns.

Fig. 03 — shallow copy leaves two Dogs sharing one Brain; deep copy gives each its own 
Dog::Dog(const Dog &other) : Animal(other) {
    brain = new Brain(*other.brain); // own allocation, contents copied — never share the pointer
}
Dog &Dog::operator=(const Dog &other) {
    Animal::operator=(other);
    *brain = *other.brain; // copy INTO the existing Brain — Brain's own operator= does the real work
    return *this;
}

"Array of Animal objects" doesn't mean what it sounds like

Taken literally, an array of plain Animal objects holding Dogs and Cats would slice every element down to just the Animal part on the way in — the exact danger flagged in the inheritance reference. What the subject actually means is an array of pointers: Animal *animals[N], each one built with new Dog() or new Cat(), and pointing at a full, unsliced object living on the heap.

"Delete directly as Animals" — the other half of this instruction

The subject isn't just asking you to delete the array — it's asking you to delete through the base pointer type, not by casting back to Dog*/Cat* first. Casting back would make the whole exercise trivial: of course the right destructor runs if you explicitly tell the compiler the real type. Deleting through the ambiguous Animal* is what actually proves virtual ~Animal() is doing the work, not you.

Once brain exists, the entire chain from Module 03 — construction base-first, destruction reverse, virtual destructor required to reach the derived class's cleanup — stops being an abstract rule and becomes the specific line of code standing between a clean valgrind run and a leaked Brain for every single element in the array.

Sheet 03 · Exercise 02 — Abstract class

AAnimal — removing the fallback entirely

A plain Animal was always a slightly awkward object — no real sound, no real identity. This exercise makes that awkwardness a compile error instead of a design smell.

The fix is one piece of syntax: change makeSound() from ordinary virtual to pure virtual, marked = 0 instead of given a body.

virtual void makeSound(void) const;      // ex00/ex01 — has a body, class stays concrete
virtual void makeSound(void) const = 0; // ex02 — no body anywhere, class becomes abstract

Two things change at once. The class-wide implementation in the .cpp file has to be deleted entirely — a pure virtual function has no definition, anywhere, in the class that declares it. And Animal a; / new Animal() now fail to compile, with an error along the lines of "cannot declare variable to be of abstract type."

Fig. 04 — the same class hierarchy, before and after one keyword change

Why nothing about Dog or Cat needs to change

This is the propagation rule made concrete: a class stays abstract only if a pure virtual function is left unimplemented somewhere in its chain. Dog::makeSound() and Cat::makeSound() already have real bodies, written back in ex00 — they satisfy the new requirement automatically, without a single line of their own code changing.

The optional A prefix

The subject allows renaming Animal to AAnimal. This is purely a naming convention, common at 42 specifically, signaling at a glance "this class exists to be inherited from, never built directly" — the compiler enforces the actual restriction regardless of what the class is called. If you rename it, the change has to be total and consistent: file names, the include guard, every constructor, and every reference to it in Dog, Cat, and main.cpp — a half-renamed class is worse than not renaming at all.

Everything from ex01 — the deep copy, the array of base pointers, the delete-through-base-type requirement — carries over completely unchanged. The abstract restriction only affects whether AAnimal itself can be built standing alone; it has no effect on ownership, destruction order, or the virtual dispatch mechanism those earlier exercises depend on.
