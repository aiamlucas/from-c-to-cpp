Sheet 00

The big picture

Module 01 is really one idea taught seven times: who owns a piece of memory, and how long do they own it for.

In C, you managed memory with malloc/free and raw addresses. Module 00 introduced std::string and classes, which hide most of that. Module 01 pulls the curtain back: new/delete, pointers and references are all different answers to the same question: where does this object live, and who is responsible for it?

Where a running program's memory lives

Every C++ program is laid out in memory as a handful of distinct regions when it runs. You don't manage most of them directly, but knowing they exist explains almost every rule in this module.

Fig. 00 — a running program's address space, top to bottom

Every variable you write lands in one of the top three regions. A local Zombie z("Foo") lands on the stack. A Zombie *z = new Zombie("Foo") puts the object on the heap and the pointer itself on the stack. A static or global variable lives in the third region for the entire run of the program. This module is entirely about the top two, because they're the only two whose lifetime you control by how you write the code.

Storage duration, in the language's own terms

The standard doesn't actually say "stack" or "heap" — those are implementation details every real compiler happens to use. The vocabulary the language itself uses is storage duration:

Storage durationCommon nameStartsEnds
Automatic"the stack"when execution reaches the declarationwhen the enclosing { } scope exits
Dynamic"the heap"when a new expression runswhen the matching delete runs — never on its own
Static"globals / statics"once, before main()once, after main() returns

"Automatic" is the key word for stack objects: their destruction is automatic, the compiler inserts the destructor call for you at the closing brace. Nothing about dynamic storage is automatic — the compiler has no way to know when you're done with heap memory, so it never calls delete for you.

Rule to internalize

Every new needs exactly one delete. Every new[] needs exactly one delete[]. Mixing them (delete on an array, or forgetting the delete entirely) is undefined behavior. This single rule is the thread running through ex00, ex01, and ex03.

What a memory leak actually is

A leak isn't the operating system losing track of bytes — it's your program losing track of the only pointer that knew an address. Once the last pointer holding a heap address is overwritten or goes out of scope without a delete, that memory becomes unreachable for the rest of the program's life. The OS reclaims it when the process exits, but until then it's dead weight your program can never use again and never frees.

Sheet 01 · Exercise 00 — BraiiiiiiinnnzzzZ

Stack vs heap

The exercise's real question: in which case is it better to allocate on the stack, and in which case the heap?

A stack object's lifetime is tied to its scope. The compiler constructs it and destroys it automatically. A heap object's lifetime is tied to nothing but your own delete call. It survives past the function that created it, which is exactly why you'd reach for it when something needs to be handed back to a caller.

What new and delete actually do

new is not just "C's malloc with a nicer name." It performs two distinct steps as a single expression:

new Zombie("Foo")

1. Ask the heap allocator for enough raw bytes to hold a Zombie.
2. Run the Zombie constructor on those bytes, exactly as if it were a normal object.

delete zombiePtr

1. Run the Zombie destructor on the object.
2. Return the raw bytes to the heap allocator so they can be reused.

malloc/free only ever did step 1/2 of each — they move bytes around but know nothing about constructors or destructors, which is exactly why they're forbidden in these modules: they can't correctly build or tear down a C++ object.

Fig. 01 — a stack zombie vs a heap zombie in the same function

Notice the diagram's own labels: heapZombie the variable is on the stack — it's a pointer, and pointers are ordinary local variables. What's on the heap is the Zombie object it points to. This is a distinction worth having crisp: "a heap object" always means there's a stack-resident pointer pointing at it, unless that pointer itself was, in turn, allocated on the heap by something else.

Constructor and destructor timing

The exercise asks for a destructor that prints a message specifically so you can see this timing rather than take it on faith. For a stack object, the destructor call is inserted by the compiler at the exact point the enclosing scope's closing brace is reached — even if that's due to an early return, an exception, or just falling off the end of a block. For a heap object, nothing calls the destructor until your own delete statement runs, which could be much later, in a completely different function, or never.

Think about it

If you never call delete on a heap zombie, does its destructor ever run during the program? What does that tell you about relying on destructor side-effects (like the print statement here) for heap objects specifically?

Default: reach for the stack. Only go to the heap when you have a concrete reason the object must outlive its creating scope, and once you do, the delete is your responsibility, not the compiler's.

Sheet 02 · Exercise 01 — Moar brainz!

Single allocation, many objects

Zombie* zombieHorde(int N, std::string name) — N objects, one allocation, one pointer back to the first.

"Single allocation" is the operative phrase. Calling new Zombie(...) N times in a loop would give you N separate allocations scattered wherever the heap happens to put them — and you'd need to track N different pointers to free them all. The array form of new, written new Zombie[N], does something different: it asks the heap for one contiguous block big enough for N objects, and hands you back a single pointer to the first one. Pointer arithmetic (horde + i) or array indexing (horde[i]) gets you to the rest.

Why horde[i] and *(horde + i) are the same thing

This is the theoretical core of the exercise, and it's why the allocation has to be contiguous. A pointer doesn't just store an address — arithmetic on it is scaled by the size of the type it points to. horde + 1 doesn't mean "add 1 to the address," it means "advance by exactly one sizeof(Zombie)." The subscript operator is defined in terms of this: horde[i] is nothing more than shorthand for *(horde + i).

Fig. 02a — pointer arithmetic is scaled by sizeof(Zombie), not by raw bytes
Fig. 02b — new Zombie[N] vs N separate new calls
Gotcha

Array new can't forward constructor arguments in C++98 — new Zombie[N](name) is not valid syntax. If Zombie's only constructor takes a name, new Zombie[N] won't compile as-is. This is the actual design decision the exercise is testing: either give Zombie a default constructor and set the name afterward through a setter, in a loop over the allocated block, or reconsider whether array-new is even the right tool here. Worth sitting with before writing any code.

The deeper reason array-new can't take constructor arguments is mechanical: new Zombie[N] has to run the same constructor call, unmodified, N times in a row over the block it just carved out. There's no slot in the syntax for "and here are N different argument lists," so the standard simply doesn't offer one — you get one shared construction step (default construction) followed by whatever per-element setup you write yourself.

Pairing rule

Whatever you allocate with new[] must be freed with delete[], never plain delete. The array form calls the destructor on every element before freeing the block; a bare delete on an array pointer only runs the first element's destructor and produces undefined behavior. This is exactly the kind of thing valgrind will catch and a quick visual read-through won't.

Under the hood, most implementations store the element count somewhere just before the block new[] returns to you, precisely so that delete[] knows how many destructors to run without you having to pass N again. That hidden bookkeeping is also part of why the two forms aren't interchangeable — delete doesn't know to look for it.

Sheet 03 · Exercise 02 — HI THIS IS BRAIN

Pointers vs references

Coming from C you already know pointers. The reference is the genuinely new idea here.

A reference is not a separate object at all. It's an alias, a second name for a variable that already exists. Nothing gets allocated, nothing gets copied. Once it's bound, it can never point anywhere else and it can never be null.

std::string name = "Alexander";
std::string &nickname = name;   // nickname is just another name for name

nickname = "Alex";                        // changes name too, they're the same variable
std::cout << name;                        // prints "Alex"
In plain terms

Think of it like calling someone by a nickname. The nickname isn't a second person standing next to them, it's just another way to refer to the one person who's there. Change what the nickname points to and you've changed the original directly, because they were never two things.

A pointer is different. It has its own address and its own storage and what it holds is another variable's address, a value you're free to change:

std::string *namePtr = &name;   // namePtr holds the address of name

*namePtr = "Xander";                     // dereference to reach name and change it
namePtr = &otherName;                   // reseat it: now it points somewhere else entirely

That's the whole difference in one line: a pointer is a box that holds an address and can be emptied or refilled; a reference isn't a box at all, just a second label taped onto a box that already exists.

Why the same symbol, &, means two different things

This is the single most common source of confusion moving from C, and it comes down to where in the code the symbol appears:

PositionExampleMeaning
In a type / declarationstd::string &r = a;"the type of r is reference-to-string" — a type modifier, exactly parallel to * meaning "pointer-to"
In an expressionptr = &a;"address-of" — produces the address of a, same meaning it always had in C

The compiler resolves which meaning applies purely from grammatical position, the same way * means "declare a pointer" in int *p; but "dereference" in *p = 5;. Neither symbol is actually ambiguous to the compiler — it only feels that way to a reader until the pattern clicks.

C doesn't have references. Not by accident, on purpose. In C, every pointer stays visible, you always see '*'. C++ hides it so two things get easier: math-like code such as a + b instead of add(&a, &b), and functions that can change a variable without any * at the call site. The closest C gets is a pointer you dereference by hand, every time:

/* the same idea, in C */
char name[20] = "Alexander";
char *nickname = name;         // arrays decay to a pointer to their first element

strcpy(nickname, "Alex");         // C has no assignment operator for whole strings
printf("%s", name);          // prints "Alex"
Under the hood

On most compilers a C++ reference compiles down to exactly that: an address stored somewhere, dereferenced automatically on every access. It isn't a different runtime mechanism from a pointer, it's the compiler agreeing to insert the * for you and refusing to ever let the address be null or reseated. The safety is a compile-time contract, not a hardware feature.

Why the exercise expects three identical addresses

This is the whole point of ex02, spelled out: &stringVar, stringPTR, and &stringREF should all print the same address. That's not a coincidence to verify and move on from — it's the proof that a reference has no independent existence in memory. A pointer has its own address (&stringPTR would be a fourth, different address, holding the third one's value); a reference doesn't, because &stringREF can only ever mean "the address of the thing it refers to." There is no other address to give.

Sheet 04 · Exercise 03 — Unnecessary violence

Composition, and choosing pointer vs reference as a member

The subject asks you to think about this before coding: when is a pointer to Weapon the right call, and when is a reference?

HumanA and HumanB both have a Weapon. That "has-a" relationship is composition, one of the two basic ways objects relate in OOP — the other being inheritance ("is-a"), which Module 04 introduces. Composition is the plainer of the two: one object simply holds, as a member, something that is itself an object of another class. What differs between HumanA and HumanB is a guarantee each class needs to make about that relationship, and the member type follows directly from the guarantee.

HumanA — always armed

Takes its Weapon in the constructor and is guaranteed to always have one. A reference member fits: it must be bound the moment the object is constructed (init list, not the constructor body), it can never be null, and it can never be pointed somewhere else afterward. That's not a limitation here — it's the guarantee "always armed" is asking for, enforced by the compiler instead of by convention.

HumanB — maybe armed

Doesn't take a Weapon at construction, and might not have one at all, or might get one later via setWeapon(). A pointer member fits: it can start out null (no weapon yet), and it can be reassigned when setWeapon() is called. Neither of those is possible with a reference.

Why reference members force the initializer list

This isn't a style preference — it's a direct consequence of the two rules from ex02 (must bind at declaration, can never be reseated), applied to the timing of object construction. By the time a constructor's body starts running, all members already exist — construction of members happens before the opening brace { of the constructor is reached. If a reference member had no initializer list entry, the compiler would need to default-construct it first and let you assign a value in the body afterward — but a reference has no default state to construct, and an assignment after the fact would be a reseat, which is illegal. The initializer list is the only point in the object's life early enough to satisfy "must bind at declaration."

class HumanA {
    Weapon &_weapon;
public:
    HumanA(Weapon &w) : _weapon(w) {}   // OK — bound during member construction

    // HumanA(Weapon &w) { _weapon = w; }   // ERROR — too late, _weapon must already exist
};

The same requirement applies to const data members, for an identical reason: a const int also has no legal "assign later," so it too must appear in the initializer list. Reference members and const members are the two cases in C++ where the initializer list stops being a style choice and becomes mandatory.

As a memberHumanA::_weapon (Weapon&)HumanB::_weapon (Weapon*)

Fig. 04 — the binding each member type actually enforces

The danger both versions share: dangling references

Neither a reference nor a pointer member owns the Weapon it refers to — HumanA and HumanB both borrow it. In the subject's own main, the Weapon club is declared before the Human and destroyed after it goes out of scope, so this is safe. But nothing in the type system stops you from constructing a Human whose Weapon is destroyed first — a local Weapon that goes out of scope while a Human still refers to it leaves that reference (or pointer) dangling, referring to memory that's no longer a valid Weapon. This is a lifetime bug the compiler cannot catch for you; it's on you to reason about which object outlives which.

Also worth noticing

getType() is specified to return a constant reference to type, not a copy. That avoids copying the string on every call while still preventing the caller from modifying the original through the returned reference — the same read-only guarantee your const getters in Contact gave you, just applied to the return value instead of the method itself.

Sheet 05 · Exercise 04 — Sed is for losers

File streams, without C functions

Open, read, transform, write — entirely through <fstream> and std::string, no fopen/fread in sight.

std::ifstream and std::ofstream are the C++ replacements for fopen-style file handles — they're RAII objects, so the file is opened in the constructor and closed automatically in the destructor. The pattern you'll lean on:

std::ifstream in(filename.c_str());
if (!in.is_open()) { // handle the error — don't assume the file exists }
std::string line;
while (std::getline(in, line)) { // process one line at a time }

RAII: the idea behind every stream, and most of C++

RAII stands for Resource Acquisition Is Initialization — an awkward name for a simple rule: tie a resource's lifetime to an object's lifetime, so the object's constructor acquires it and its destructor releases it. You've already used this without the name attached — every Zombie, every std::string, is doing some version of it. A file handle is just another resource, and ifstream/ofstream apply the exact same idea:

Constructor acquires

std::ifstream in(name.c_str()); opens the file the moment the object is constructed. No separate "open" call needed.

Destructor releases

When in goes out of scope — end of a function, end of a block — its destructor closes the file automatically, even if you never call close() yourself.

This is precisely why C's fopen/fclose pair is forbidden here, beyond it just being "the C way": a raw FILE* has no destructor, so nothing closes it automatically if you return early or an exception unwinds the stack. RAII removes an entire category of bug — the forgotten cleanup call — by construction.

How a stream reports success or failure

A stream object internally tracks a small set of state flags, and this is what makes constructs like while (std::getline(in, line)) work at all: the stream converts to a boolean-like value that's true while it's still in a good, readable state, and false once something's gone wrong or the file has ended.

FlagSet when
goodbiteverything is fine — the default, healthy state
eofbita read reached the end of the file
failbitan operation failed in a recoverable way, e.g. reading past the end
badbita serious, likely unrecoverable I/O error

is_open() checks specifically whether the underlying file handle attached successfully — worth checking right after construction, since a missing file doesn't throw, it just leaves the stream unable to do anything useful.

The catch

std::string::replace is explicitly forbidden. The other string members are fair game though — find() to locate each occurrence and substr() to build the output piece by piece around it is the standard route: find the next match, append everything before it plus s2 to a result string, advance your search position past the match, repeat until find() returns std::string::npos.

Why find() + a loop actually terminates

std::string::npos is not "negative one" conceptually, even though it's implemented as the largest possible value of an unsigned type — it's a dedicated sentinel meaning "no valid position exists." Every call to find(s1, pos) either returns a real index strictly greater than or equal to pos, or returns npos. Because each successful match advances your search position past the end of that match before the next call, the sequence of returned positions is strictly increasing until the moment it can't find anything else — which is exactly when the loop is guaranteed to end.

Edge cases worth testing yourself, since the subject asks for your own tests: an empty file, s1 not present at all, s1 and s2 being the same string, and s1 occurring at the very start or end of the file.

Sheet 06 · Exercise 05 — Harl 2.0

Pointers to member functions

The goal stated directly in the subject: dispatch without a forest of if/else if/else.

A pointer to a member function isn't like a regular function pointer, it can't be called on its own, because a member function implicitly needs an object (a this) to run against. The syntax reflects that: it's a pointer scoped to the class, and calling it requires supplying an object alongside it.

What this actually is, and why it matters here

Every non-static member function secretly takes one extra, invisible parameter: a pointer to the object it's being called on. When you write harl.debug(), the compiler is really generating something closer to Harl::debug(&harl), and inside debug(), the keyword this refers to that same pointer. This is precisely why a plain function pointer can't hold a member function's address — a plain function pointer's type has no room for "and also, which object." A pointer-to-member-function's type does: it's defined in terms of the class, so that when you eventually call it, you supply the missing object and the compiler fills in the invisible parameter for you.

void (Logger::*handler)(void) = &Logger::warn;
(myLogger.*handler)();      // via an object
(this->*handler)();         // via this, from inside a member function
  • void (Logger::*handler)(void) — declares handler as "a pointer to a member function of Logger, taking no args, returning void." The Logger:: inside the parens is what makes this a member-function pointer instead of an ordinary function pointer.
  • &Logger::warn — you must qualify with the class name here, even from inside the class itself. Just &warn won't compile.
  • .* and ->* — the "pointer-to-member" dereference operators. They bind the function pointer to an actual object before the call happens, which is the missing this a member function needs.

The dispatch table pattern

For Harl, this generalizes into an array: four pointers-to-member-functions, one per level, indexed in the same order as the levels. This structure has a name — a dispatch table (or jump table): instead of a chain of conditionals deciding which code to run, you compute an index once and let the array itself hold the "which." complain(level) then becomes "find the index for this level string, call (this->*array[index])()" — no branching on behavior at all, just a lookup.

A typedef is optional but worth knowing about, purely for readability: typedef void (Harl::*HarlFunc)(void); lets you write HarlFunc funcs[4] = {...}; instead of repeating the full void (Harl::*...)(void) array syntax. It changes nothing about the mechanism, only how it reads.

Why debug/info/warning/error are private

Only complain() should be a valid entry point from outside the class — callers pick a level, not a specific rant. Keeping the four level methods private and dispatching through one public method is the same encapsulation instinct as Contact's getters/setters, just applied to behavior instead of data. And since complain() is itself a member of Harl, it's allowed to call private members of the same class freely — access control is per-class, not per-function.

Sheet 07 · Exercise 06 — Harl filter (optional)

Switch statements & fallthrough

"Display all messages from this level and above" is a fallthrough problem in disguise.

switch jumps to the matching case label and then keeps executing forward through every subsequent case until it hits a break. It doesn't stop at the end of the matched case on its own. That's usually the bug you guard against with a break in every case. Here it's the feature: if levels are ordered DEBUG → INFO → WARNING → ERROR and you omit the break, matching WARNING and falling through naturally prints WARNING and everything below it.

Why this behaves the way it does

A switch is really just a labeled jump, closer to a goto than to a series of if statements, which is exactly why compilers can often implement it as a genuine jump table for dense, consecutive case values: compute the index once, jump directly to the matching label, and let execution simply fall forward through the code, exactly like it would through any other unlabelled sequence of statements without a jump in between. break is not part of falling through being prevented by default — it's an explicit jump out of the switch, inserted by you, at the one place you want execution to stop.

Fig. 05 — matching WARNING falls through to ERROR when there's no break

Why you can't switch on a std::string

A switch only accepts values of an integral type — int, char, enum, and similar — because the whole mechanism is built around comparing a single number against a set of compile-time constant labels. A std::string is a class, not an integral value, and case labels have to be constants known at compile time, which rules out runtime string comparison entirely. The practical consequence for this exercise: you first have to translate the level string into an integer — the natural choice is looping over a small array of known level names to find a matching index — and only then can switch operate on that index.

This two-step shape — map the real-world input to a small integer, then switch on the integer — is a common pattern anywhere you need switch-like dispatch on something that isn't naturally numeric.

Second half of the exercise

The subject also wants a fallback for input that doesn't match any known level — that's switch's default: case, which catches anything the earlier case labels didn't match, including your own "no valid index found" sentinel value (like -1) if you use one.
