Sheet 00

The big picture

Module 02 taught a class to behave like a value. Module 03 teaches one class to be another — with everything that implies about construction order, access, and what happens when two parents share a grandparent.

You already met the other way objects relate, back in Module 02 ex03: HumanA has a Weapon, stored as a member. That's composition. This module introduces the second relationship OOP is built on: inheritance, where one class is a more specific version of another. A ScavTrap doesn't hold a ClapTrap as a member — it is one, plus something extra.

has-a — composition (Module 02)

HumanA holds a Weapon& as a member. Two separate objects, one referring to the other. HumanA is not a Weapon.

is-a — inheritance (this module)

ScavTrap inherits from ClapTrap. There is one object. Every ScavTrap genuinely is a ClapTrap, with more attached.

Access control gets a middle tier

Module 02 only needed private and public. Inheritance introduces the reason protected exists: a derived class needs to touch its base class's data directly — ScavTrap::attack() needs _attackDamage — but the outside world still shouldn't. protected is exactly that middle ground.

Access levelVisible to the class itselfVisible to a derived classVisible outside
privateYesNoNo
protectedYesYesNo
publicYesYesYes

This is the actual design decision buried in ex00's instructions: ClapTrap's attributes need to be protected, not private, specifically so ScavTrap and FragTrap can read and modify them without going through a setter for every single field.

Sheet 01 · Exercise 00 — Aaaaand... OPEN!

ClapTrap — the base class

No inheritance happens yet. This exercise is entirely about building a base solid enough for two more classes to stand on next.

ClapTrap is an ordinary class by every rule you already know from Module 02: Orthodox Canonical Form, private-by-default data, public member functions that print a message so the evaluator can see what fired. The only thing genuinely new is that you're not just building a class — you're building the foundation every later exercise inherits, which changes one decision: private vs protected.

AttributeInitial valueMeaning
nameconstructor parameteridentifies this ClapTrap in every printed message
hitPoints10health — at 0, the ClapTrap can't act
energyPoints10stamina — every action costs 1, at 0 it can't act
attackDamage0how much a target loses per attack

The action-gating logic every member function repeats

attack(), takeDamage(), and beRepaired() all share the same shape: check whether the ClapTrap is even able to act, do the thing, print a message. The subject spells this out directly — "ClapTrap can't do anything if it has no hit points or energy points left" — which turns each function into a guard clause plus one line of logic.

void ClapTrap::attack(const std::string& target) {
    if (_hitPoints == 0 || _energyPoints == 0)
        return; // nothing to do — no energy or no health left
    _energyPoints--;
    std::cout << "ClapTrap " << _name << " attacks " << target
              << ", causing " << _attackDamage << " points of damage!" << std::endl;
}

takeDamage and beRepaired follow the identical shape: guard, spend 1 energy, apply the effect, print. The only variation is which attribute moves and in which direction. Worth also deciding what happens if takeDamage would take hit points below zero — clamping to 0 rather than letting an unsigned int underflow into a huge number is the safer call, since the parameter type is unsigned int.

Why protected, not private

Nothing in ex00 alone requires protected — a fully private ClapTrap compiles and works perfectly on its own. The reason to choose protected here is entirely forward-looking: ex01's ScavTrap::attack() needs to read _attackDamage directly to print its own message, and a derived class has no special access to a private base member — inheritance does not bypass private. Get this wrong in ex00 and you're editing ClapTrap.hpp again in ex01.

Sheet 02 · Exercise 01 — Serena, my love!

ScavTrap — single inheritance, and construction order

class ScavTrap : public ClapTrap — three words that change what happens the instant a ScavTrap is born.

class ScavTrap : public ClapTrap {
public:
    ScavTrap(std::string name);
    ~ScavTrap();
    void attack(const std::string& target); // redefines ClapTrap's version
    void guardGate(void);                        // new, ScavTrap-only
};

The public in : public ClapTrap is doing real work: it means every public member of ClapTrap stays public in ScavTrap, and every protected member stays protected — the access levels carry through unchanged. This is the form you'll use almost always in this module; private and protected inheritance exist but deliberately break the is-a relationship from the outside, which isn't what any of these exercises want.

Why the compiler insists on constructing the base first

A ScavTrap object physically contains a ClapTrap as its first part in memory. Before any ScavTrap-specific code can safely run — code that might rely on _hitPoints already being a sane number — that ClapTrap portion has to already exist and be fully initialized. The language enforces this as a hard rule, not a convention: the base class constructor always runs to completion before the derived class constructor's own body starts.

Fig. 01 — construction runs base-first; destruction unwinds in reverse

Destruction is the same rule read backwards, and for the same reason: ScavTrap's own logic might depend on the ClapTrap part still being valid while it tears down its own additions, so the base can't be destroyed first out from under it. Whatever was built last must be the first thing removed — the subject asks you to prove this with your own test specifically because it's easy to state and easy to get backwards from memory.

Calling the base constructor explicitly

If you write nothing, the compiler tries to call ClapTrap's default constructor automatically, before your ScavTrap body runs. That's rarely what you want here — you have a name parameter you need to forward. The initializer list is where you say which base constructor to use instead:

ScavTrap::ScavTrap(std::string name) : ClapTrap(name) {
    _hitPoints    = 100;
    _energyPoints = 50;
    _attackDamage = 20;
    std::cout << "ScavTrap " << _name << " is ready for battle!" << std::endl;
}

ClapTrap(name) in the initializer list isn't a function call happening during ScavTrap's construction — it's telling the compiler which base constructor to run as step one, before anything in the body executes. By the time the body's first line runs, _hitPoints already holds ClapTrap's default of 10; the body then overwrites it to 100. Some implementations skip the redundant default-then-overwrite by giving ClapTrap a protected constructor that takes all four values directly — either approach is fine, as long as construction order is visibly correct in your test output.

Redefining attack(): hiding, not yet overriding

ScavTrap declares its own attack(const std::string&) with the identical signature as ClapTrap's. This is called name hiding: inside ScavTrap's scope, the name attack now refers to ScavTrap's version, and ClapTrap's version is hidden (though still reachable by explicitly writing ClapTrap::attack(...)).

Worth sitting with

Called on a ScavTrap object or through a ScavTrap*, you get ScavTrap::attack(). But this resolution happens by looking at the static type of the expression — the type known at compile time — not by asking the actual object what it is at runtime. Call through a ClapTrap* that happens to point at a ScavTrap, and without the virtual keyword, you'd get ClapTrap::attack() instead: the base version, even though the object underneath is really a ScavTrap. Module 04 introduces virtual specifically to fix this — true runtime polymorphism, decided by what the object actually is, not by the type of the pointer holding it.

The exercise's own title is the point: nothing new to learn here, only whether ex01's pattern actually became automatic.

FragTrap inherits from ClapTrap exactly the way ScavTrap does — same public inheritance, same explicit base-constructor call in the initializer list, same construction-then-destruction chaining your test has to demonstrate again. Only the numbers and the messages differ.

Sheet 04 · Exercise 03 (optional) — Now it's weird!

DiamondTrap — multiple inheritance, and the diamond problem

DiamondTrap inherits from both ScavTrap and FragTrap — and both of those already inherit from ClapTrap. Draw the arrows and you get a diamond.

C++ allows a class to inherit from more than one base at once — class DiamondTrap : public ScavTrap, public FragTrap. Taken alone, that's a simple extension of everything ex01 and ex02 already taught. The complication is what happens because ScavTrap and FragTrap don't just resemble each other — they share an actual ancestor.

Fig. 02 — without virtual inheritance, ClapTrap gets built twice

Without any special handling, DiamondTrap ends up containing two entirely separate ClapTrap sub-objects — one built through the ScavTrap path, one through the FragTrap path. This is the classic diamond problem. It's not just wasted memory: it also means diamondTrap.attack() or a plain reference to hitPoints becomes genuinely ambiguous — the compiler can't tell which of the two ClapTrap copies you mean, and refuses to compile until you disambiguate every single access.

The fix: virtual inheritance

C++'s answer is the virtual keyword on the base-class specifier itself — not on a function this time, on the inheritance relationship:

class ScavTrap : virtual public ClapTrap { /* ... */ };
class FragTrap  : virtual public ClapTrap { /* ... */ };

virtual public ClapTrap tells the compiler: however many paths lead back to ClapTrap, keep exactly one shared sub-object. Both ScavTrap's and FragTrap's inherited ClapTrap parts become the same piece of memory once they're combined in DiamondTrap.

Fig. 03 — with virtual inheritance, both paths converge on one shared ClapTrap
The trade-off virtual inheritance makes

Sharing the base changes who is responsible for constructing it. Normally a derived class's initializer list calling ClapTrap(name) is exactly what builds the base. With a virtual base, that call from ScavTrap's or FragTrap's own initializer list is ignored whenever they're used as part of a more-derived object like DiamondTrap. Instead, the most-derived class — DiamondTrap itself — becomes directly responsible for constructing the shared virtual base, bypassing the intermediate classes entirely. This is exactly why the subject says "the ClapTrap instance of DiamondTrap will be created once, and only once" — it's not a hint, it's describing what virtual inheritance now guarantees mechanically.

DiamondTrap::DiamondTrap(std::string name)
    : ClapTrap(name + "_clap_name"),  // DiamondTrap constructs the shared base directly
      ScavTrap(name), FragTrap(name),      // their own ClapTrap(...) calls are ignored here
      _name(name)
{ /* ... */ }

One name, deliberately shadowed

The subject requires DiamondTrap to have its own attribute, spelled with the exact same identifier ClapTrap uses for its own name — if the base calls it name, the derived one is also name. This is shadowing: inside DiamondTrap's own code, the closer, derived name wins ordinary lookup and hides the base one, exactly the same "nearest scope wins" rule that hid ClapTrap::attack() in ex01. To reach the base's copy explicitly, you qualify it: ClapTrap::name.

Fig. 04 — DiamondTrap::name shadows ClapTrap::name; the base one still exists, reachable by qualifying it

whoAmI() exists precisely to print both: name on its own (the derived one, found through ordinary lookup) and ClapTrap::name explicitly (forcing lookup to skip past the shadowing one). The "_clap_name" suffix in the constructor is what keeps the two values visibly distinct in your own tests, so you can actually see which one printed where.

-Wshadow and -Wno-shadow

-Wshadow is a compiler warning flag that fires whenever an inner declaration hides an outer one with the same name — exactly the situation DiamondTrap::name vs ClapTrap::name creates on purpose. Since this exercise requires the shadowing, compiling with -Wshadow would flag legitimate, intentional code as a warning; -Wno-shadow turns that specific warning back off. The subject asking if you know both flags is really asking whether you understand that this warning exists for good reason in general, but this one case is a deliberate, documented exception to it.

Which attack() wins

DiamondTrap inherits attack() from both ScavTrap and FragTrap, and they're genuinely different functions with different messages. An unqualified call to attack() inside DiamondTrap is ambiguous for the same reason the doubled ClapTrap attributes were, before virtual inheritance fixed that half of the problem — two equally-good candidates, no way for the compiler to prefer one. The subject resolves this explicitly: attack() (ScavTrap). A using ScavTrap::attack; declaration inside DiamondTrap, or simply calling ScavTrap::attack(target) directly from within your own attack() override, pulls in exactly the one you're told to use.

Notice only attack() needed disambiguating — guardGate() and highFivesGuys() have no naming collision at all, since ScavTrap and FragTrap each only define their own. Ambiguity in multiple inheritance is always about a shared name, not about inheriting from two classes in general.
