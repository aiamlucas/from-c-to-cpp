Sheet 00

When this is actually worth doing

Not every C++ concept pays off at this level. A quick filter before reaching for assembly or gdb.

Worth it

Pointers, references, virtual dispatch, memory layout, copy semantics, alignment. Anywhere a C++ rule feels arbitrary and "why does this cost something" isn't obvious from the language alone.

Usually not

Templates (one call generates many near-identical blocks), STL container internals, exception handling. The abstraction is doing its job here — digging in adds noise, not insight, this early.

Generating real assembly, not guessed assembly

g++ -S -O0 -fno-asynchronous-unwind-tables -masm=intel file.cpp -o file.s

-O0 matters — without it, the optimizer inlines and rewrites things, and the output stops matching your source line-for-line. -masm=intel gives the more readable dest, src ordering instead of the default AT&T syntax.

Sheet 01

The big picture — CPU, RAM, the stack, and VRAM

Registers are the only thing physically inside the CPU chip. Everything else — the stack included — is a room down the hall, reached over a wire.

The CPU chip itself is tiny and holds almost nothing on its own: a handful of registers, and the circuitry to do arithmetic and follow instructions. Everything a running program actually needs — its variables, its call history, its compiled code — lives somewhere else, physically separate from the chip, and has to be fetched across a connection every time it's needed.

The stack, precisely

The subject line: the stack is not a hardware feature of the CPU. It is an ordinary region of RAM — the same memory that holds the heap, global variables, and your compiled code. What makes it "the stack" is pure convention: it grows downward, one specific register (rsp, the stack pointer) always holds the address of its current top, and the instructions call/ret/push/pop automatically adjust rsp as functions are entered and left.

A callback you've already seen without knowing it

Back in the gdb section, the very first disassembled instruction was mov rax, [rbp-0x8]. That's rbp — the base pointer, a second special register that holds a stable reference point for the current function's region of the stack. [rbp-0x8] means "the local variable stored 8 bytes below this function's base" — which is exactly how a local variable like a gets read off the stack, in RAM, into a register, so the CPU can actually work with it.

Kinds of registers

RegisterKindHolds
rax, rbx, rcx, rdx, rsi, rdi, r8–r15general-purposewhatever the compiler needs, per the calling convention (Sheet 02)
ripspecial — instruction pointerthe address of the instruction currently executing. This is what [rip+16] addressing, from Sheet 04, is relative to.
rspspecial — stack pointerthe address of the current top of the stack, in RAM
rbpspecial — base/frame pointera stable anchor for the current function's own slice of the stack — local variables are read as offsets from it, like [rbp-0x8]
rflagsspecial — status flagsbits set automatically by arithmetic/comparison instructions (zero, carry, sign, overflow), read by conditional jumps

The bus

The bus is the physical set of connections — wires, on the actual circuit board — carrying addresses, data, and control signals between the CPU and everything outside it. When mov rax, [address] runs, the address travels out over the bus to RAM; RAM sends the requested bytes back over the bus into rax. That round trip is the entire reason register access is fast and RAM access is comparatively slow: a register never leaves the chip at all, while RAM always costs a trip across the bus, there and back.

RAM

RAM (Random Access Memory) is the computer's main working memory — separate chips, sitting next to the CPU on the motherboard. Everything a running program uses beyond its literal registers lives here: the stack, the heap, global and static variables, and even the compiled machine code itself, loaded into RAM before the CPU can execute a single instruction of it. Vastly bigger than the register file (gigabytes versus a handful of 8-byte slots), at the cost of every single access needing that bus round trip.

VRAM

VRAM is memory that lives physically on the graphics card itself — a separate chip again, this time sitting right next to the GPU rather than the CPU. The GPU does enormous amounts of highly parallel work (rendering, shading) that needs to read and write huge quantities of data extremely fast, so it gets its own dedicated, very-high-bandwidth memory rather than sharing the CPU's RAM. Getting data from the CPU's RAM into VRAM requires an explicit transfer across a separate, slower connection (commonly PCIe) — which is exactly why "uploading a texture to the GPU" is a distinct, deliberate, relatively costly step in graphics programming, never something that happens for free.

Sheet 02

Registers & the calling convention

Physically identical hardware. The only difference between them is which job the calling convention habitually assigns.

A register is a tiny storage slot built directly into the CPU chip — not RAM, not the stack. On x86-64, every general-purpose register holds exactly 64 bits (8 bytes), matching the width of a pointer on this platform — not a coincidence. Every register is physically identical; the names carry no built-in meaning.

RegisterConventional job
rdi1st integer/pointer argument to a function
rsi2nd argument
rdx3rd argument — or, if unused, free scratch space
rcx4th argument
raxreturn value; general-purpose scratch

The whole convention exists for one reason: so code compiled in one file can call a function compiled in a completely different file, and both sides agree on where to find the arguments, without ever seeing each other's source.

Sheet 03

The core instructions

Four instructions cover almost everything in the traces below.

InstructionPlain English
mov X, YCopy the value in Y into X. Think X = Y.
mov X, [Y][Y] means "go to the address in Y, read what's stored there" — a dereference, the assembly equivalent of C++'s *ptr.
lea X, Y"Load Effective Address" — compute what address Y is, store that address itself in X. Never touches memory at Y — pure address arithmetic.
call XJump to X, run it, come back when done. If X is a name, the target was fixed at compile time. If X is a register, the target was read from memory and could differ every time this line runs.
Sheet 04

Virtual dispatch, fully traced

Non-virtual: go straight there. Virtual: ask, then go.

class Animal {
public:
    virtual void makeSound() const {}
    void nonVirtualFunc() const {}
};
class Dog : public Animal {
public:
    void makeSound() const {}
};
One fact worth having before the assembly

Every member function secretly receives the object it's called on as an invisible first argument — that's what the keyword this refers to. Below, whenever a comment says "this pointer," it means: the address of the object the function is running on.

Non-virtual — a->nonVirtualFunc()

mov  rax, [a]                        ; rax = a
mov  rdi, rax                        ; rdi = a — this becomes nonVirtualFunc()'s hidden "this"
call _ZNK6Animal14nonVirtualFuncEv   ; jump straight to Animal::nonVirtualFunc — see note below

Three instructions. The compiler knew the target while compiling — nothing left to figure out at runtime.

_ZNK6Animal14nonVirtualFuncEv isn't gibberish — it's name mangling, the compiler's way of encoding Animal::nonVirtualFunc() const into one unique string, since C++ allows overloading and the binary needs a distinct name per function. You never read these by hand; this whole ugly string simply is the function.

Fig. 03 — the non-virtual path, for direct comparison against Fig. 04 below

Virtual — a->makeSound(), where a really points at a Dog

Concretely: suppose main did Dog d; Animal *a = &d;, so a genuinely points at a real Dog.

StepInstructionWhat it does, concretelyState after
1mov rax, [a]Read the value of the variable a — which holds d's addressrax = address of d
2mov rax, [rax]Follow that address, read the first 8 bytes stored there — every object's hidden vptr lives exactly thererax = address of Dog's vtable
3mov rdx, [rax]Follow the vtable's address, read its very first slotrdx = the real address of Dog::makeSound's code
4mov rax, [a]Re-read a — d's address is needed again, this time to hand it over as thisrax = address of d, again
5mov rdi, raxPlace d's address into rdi — this becomes Dog::makeSound's hidden thisrdi = this = address of d
6call rdxJump to whatever address is sitting in rdx — proven, two steps ago, to be Dog::makeSound's real codelands exactly on Dog::makeSound
 
mov  rax, [a]           ; rax = a's value = the Dog object's address
mov  rax, [rax]         ; rax = *a → the object's hidden vptr
mov  rdx, [rax]         ; rdx = the real address of Dog::makeSound, read from the vtable
mov  rax, [a]           ; rax = the Dog's address, again
mov  rdi, rax           ; rdi = this = the Dog's address
call rdx                ; jump to whatever's in rdx — a value, not a name

Six instructions. Two extra reads (object→vptr, vptr→function address) before the jump. The compiler could not know this address while compiling — only the object knows, only once the program is running.

Fig. 04 — the exact chain "call rdx" is following, traced one instruction at a time

Where the vptr gets set — once, at construction

lea  rax, _ZTV3Dog[rip+16]   ; rax = address of Dog's vtable (compiled-in data, one copy per class)
mov  [d], rax                ; write that address into d's first 8 bytes — this IS the vptr being set
PieceWhat it means
_ZTV3DogMangled name for "vtable for Dog" — ready-made data baked into the binary. One copy total, shared by every Dog object ever created.
[rip+16]rip = address of the currently-running instruction. Addressing relative to it lets the binary load anywhere in memory. +16 skips two 8-byte bookkeeping entries (type info, multiple-inheritance offset) that sit before the real function pointers in every vtable.
vptr"virtual table pointer" — a pointer stored in the object itself, aimed at that object's own class's vtable. Set once, at construction, unchanged for the object's whole life.
Sheet 05

Memory cost, measured

Not guessed — printed, from real addresses.

class NoVirtual  { int x; };                            // sizeof = 4
class HasVirtual { int x; public: virtual void f(){}; }; // sizeof = 16

Measured directly: the vptr sits at byte 0, the int at byte 8. 8 + 4 = 12 bytes of real data — sizeof reports 16. The missing 4 bytes are alignment padding: a CPU reads an 8-byte value fastest at an 8-byte-aligned address, so the compiler pads the whole object's size up to a multiple of 8 — guaranteeing every element in an array of these objects starts cleanly aligned, not just the first one.

Fig. 05 — 12 real bytes, 4 padding bytes, so every array element lands on an 8-byte boundary

vptr stands for virtual table pointer (sometimes shortened to "virtual pointer") — a pointer, stored in the object itself, aimed at that object's own class's vtable.

Fig. 06 — why the padding exists: not wasted space, the price of every array element starting aligned
Sheet 06

Verifying it live — gdb on ex00

Everything above, checked against the real, compiled Animal/Dog/Cat binary — not a toy example.

Step 1 — compile with debug symbols

Normal -Wall -Wextra -Werror builds strip out the information gdb needs to map instructions back to source lines and variable names. Add -g for a debug build:

c++ -g -Wall -Wextra -Werror -std=c++98 Animal.cpp Cat.cpp Dog.cpp WrongAnimal.cpp WrongCat.cpp main.cpp -o animal_dbg

If your Makefile already has a DEBUG=1 pattern adding -g -O0 to CFLAGS (worth having, going forward), just run make DEBUG=1 instead.

Step 2 — turn on TUI split mode: source and assembly, both visible, always

$ gdb ./animal_dbg (gdb) set disassembly-flavor intel (gdb) layout split

layout split divides the screen into three stacked panes: your C++ source on top, live disassembly in the middle, and the normal command prompt at the bottom — all visible at once, all updating together as you step.

Fig. 07 — one C++ line (highlighted top) maps to six assembly instructions (highlighted middle); the arrows move together as you step
The one navigation quirk

Typing normally goes to the bottom CMD pane. To scroll the ASM pane by hand (rather than stepping through it), press Ctrl+X then O to shift keyboard focus onto it first — otherwise arrow keys just scroll gdb's command history. Ctrl+L redraws the screen if it ever looks visually garbled after a terminal resize.

Step 3 — break, run, and watch both panes move together

(gdb) break main (gdb) run ... SRC pane jumps to main.cpp, arrow on the breakpoint line (gdb) next ... step until just past: Animal *j = new Dog();

Step 4 — ask gdb what j actually is

(gdb) print j $1 = (const Animal *) 0x5555555592c0 (gdb) print *j $2 = (Dog) {<Animal> = {_type = "Dog"}} ↑ gdb reports the REAL dynamic type — Dog — not the declared Animal*

gdb reads the object's own vptr to determine its true type for display purposes — the same mechanism from the assembly trace, used here by the debugger itself.

Step 5 — read the vptr directly, as raw bytes

(gdb) print *(void**)j $3 = (void *) 0x555555557d38 (gdb) info symbol *(void**)j vtable for Dog + 16 in section .data.rel.ro ↑ confirms: the object's first 8 bytes really do point at Dog's vtable, past the +16 offset

Step 6 — break inside Dog::makeSound, prove it's reached through the base pointer

(gdb) break Dog::makeSound (gdb) continue ... SRC pane jumps into Dog.cpp — stopped inside Dog::makeSound, even though the call site only had an Animal* (gdb) bt #0 Dog::makeSound (this=0x5555555592c0) const at Dog.cpp:41 #1 0x... in main () at main.cpp:19

Step 7 — now the payoff: stepi, watching both panes and the registers together

(gdb) stepi ... ASM pane's arrow advances one line; SRC pane stays on the calling line (gdb) print $rax $4 = (void *) 0x555555557d38 the vtable address (gdb) stepi (gdb) print $rdx $5 = (void *) 0x555555555289 Dog::makeSound's real code address (gdb) stepi (gdb) print $rdi $6 = (void *) 0x5555555592c0 the Dog object's address — this

This is the live version of Sheet 03's six-row instruction table — the exact same values, watched appear one stepi at a time, with the ASM pane's highlighted line and the register value changing in lockstep. print $rax reads a register directly; the $ prefix is gdb's syntax for "this is a register, not a variable."

Quick reference — the commands used above

layout split show source + assembly together · Ctrl+X O switch pane focus · break <func> set a breakpoint · run / continue start or resume · next step one C++ line, skip over calls · step step one C++ line, into calls · stepi step one machine instruction · print <expr> evaluate and show · print $rax read a register directly · bt backtrace, the call stack · info symbol <addr> resolve an address back to a name.

Sheet 07

nvim-dap — the same workflow, with a UI

Everything in Sheet 05 works exactly the same underneath — nvim-dap just wraps gdb's output in breakpoint gutters, a variables panel, and a call-stack view, instead of typing print statements by hand.

Minimal setup, if not already configured

-- requires: nvim-dap, nvim-dap-ui (optional but recommended), gdb installed
local dap = require("dap")

dap.adapters.gdb = {
  type = "executable",
  command = "gdb",
  args = { "-i", "dap" }
}

dap.configurations.cpp = {
  {
    name = "Launch (gdb, cpp04 ex00)",
    type = "gdb",
    request = "launch",
    program = function()
      return vim.fn.input("Path to executable: ", vim.fn.getcwd() .. "/", "file")
    end,
    cwd = "${workspaceFolder}",
    stopAtBeginningOfMainSubprogram = false,
  },
}

Where nvim-dap alone isn't quite enough

nvim-dap-ui is built around C++-level concepts — variables, the call stack, breakpoints on source lines. It doesn't expose raw register contents or x/2gx-style memory examination out of the box. For anything at the level of Sheet 05's Steps 4–7 — reading the vptr as raw bytes, watching rax/rdx/rdi fill in — you can still reach the underlying gdb console directly with :lua require('dap').repl.open(), which drops you into the exact same gdb prompt used throughout Sheet 05, commands and all, without leaving Neovim.

In practice: use nvim-dap-ui for the everyday case — "why is this value wrong," "did this branch actually run," stepping through your own Dog/Cat logic with breakpoints and a visible variables panel. Drop into the raw gdb REPL specifically when the question is about the mechanism itself — vptrs, register contents, raw memory — the same territory Sheet 05 covers.
