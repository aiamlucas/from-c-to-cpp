Sheet 00

The big picture

Module 02 asks what it means for your own type to behave like a real value — something you can copy, compare, and do arithmetic on, the same way you already do with int or float.

Module 01 taught you to build classes and manage memory. Module 02 is about giving a class the same rights built-in types get automatically. Two threads run through every exercise here:

Orthodox Canonical Form

A guarantee that your class copies, assigns, and destroys itself correctly, spelled out explicitly instead of left to whatever the compiler silently generates.

Ad-hoc polymorphism

The module's own name for operator overloading — teaching +, ==, << and friends to understand your type, resolved entirely at compile time.

Everything in ex00–ex03 builds one running example: a fixed-point number class, Fixed. By the end it behaves close enough to a built-in numeric type that you can write a + b, a < b, ++a, and std::cout << a

Sheet 01

The Orthodox Canonical Form

Four member functions every class secretly has already — canonical form just means writing them yourself, on purpose.

Here's the part that surprises people coming from Module 01: every class you've ever written already has these four member functions, whether you wrote them or not. If you declare none of them, the compiler silently generates all four for you, doing the simplest possible thing — copy each member, do nothing special on destruction. Orthodox Canonical Form means you stop relying on that silent, automatic version and write all four explicitly, even when the implementation ends up trivial.

MemberSignatureRuns when…

Copy constructorFixed(const Fixed &src);a new object is created directly from an existing one: Fixed b(a);
Copy assignment operatorFixed &operator=(const Fixed &rhs);an already-existing object is overwritten by another: c = b;
Destructor~Fixed();the object's lifetime ends — scope exit, delete, or program end
Fig. 01 — the four canonical members, at a glance

construction vs assignment

The subject's own example in ex00 is designed to make this exact point:

Fixed a;        // default constructor
Fixed b( a );   // copy CONSTRUCTOR — b doesn't exist yet
Fixed c;        // default constructor, again
c = b;          // copy ASSIGNMENT — c already exists
  • Fixed b( a ); — there is no b before this line. C++ has to build one from scratch, using a's value as the source. That's the copy constructor's job.
  • c = b; — c already exists (it was default-constructed one line earlier). This line doesn't create anything new — it overwrites c's existing value with b's. That's the copy assignment operator's job.

Same-looking syntax can hide the same distinction: Fixed b = a; (with an = at the point of declaration) is still the copy constructor, not assignment; because b is being created on that line, not overwritten. The rule is purely about whether the left-hand object already exists the moment before this line runs.

Gotcha in the subject's own sample output

The subject marks one line "may be missing depending on your implementation". That's copy elision: compilers are allowed to skip a copy entirely in certain situations (most commonly, returning a local object by value). Fewer "copy constructor called" prints than you expected is very likely the compiler legally optimizing a copy away — not a bug in your class.

Why bother, if the compiler already writes these by default?

For Fixed specifically a class holding one plain int, the compiler-generated versions would actually work fine. The real payoff of this discipline shows up later, once a class owns something the compiler can't safely copy by just duplicating bytes: a pointer to heap memory, a file handle, anything with a lifetime of its own. Copying a pointer byte-for-byte gives you two objects pointing at the same memory — a shallow copy — and the first one to get destroyed frees memory the second one still thinks it owns.

This is often called the Rule of Three (the C++98-era version of what later standards extended into a Rule of Five): if a class needs a custom destructor, copy constructor, or copy assignment operator, it almost certainly needs all three, because all three exist to answer the same question: what does it actually mean to copy or destroy this object? Fixed doesn't need custom logic yet to answer that question correctly. Writing the four members explicitly now is the habit that pays off the moment a class does.

Sheet 02 · Exercise 00 — My First Class in Orthodox Canonical Form

Fixed-point numbers, in their simplest form

A class that can only represent the value 0.0 — on purpose, so the canonical form itself is the entire exercise.

Fixed-point isn't a C++ feature, it's a convention. Fixed stores one plain int, and the class simply agrees to interpret that integer as if it had an imaginary binary point somewhere in the middle. With 8 fractional bits, the raw integer 256 is understood to mean 1.0, because 256 / 2⁸ = 1. Nothing about the bits themselves changed, only how the class chooses to read them.

Fig. 02 — one raw int, read as an integer part and a fractional part

static const int — the fractional bit count

static on a member means there is exactly one copy of it, shared by every Fixed object that will ever exist. Conceptually it belongs to the class, not to any particular instance.

C++98 gotcha

A static const int is one of the few members you're allowed to give a value directly inside the class body: static const int fractionalBits = 8;

Sheet 03 · Exercise 01 — Towards a more useful fixed-point number class

Conversions, and the insertion operator

Turning an int or a float into raw bits, turning raw bits back, and teaching << to print the result.

Two new constructors need to do the opposite jobs of each other: take a familiar number, and store it as the raw fixed-point representation this class actually keeps internally. And two more member functions, toFloat() and toInt(), need to undo that exact process — take the raw representation and hand back something readable again.

Fig. 03 — converting into Fixed's raw representation

Watching the bits actually move

num << fractionalBits isn't a metaphor for multiplying by 256 — it is multiplying by 256, at the bit level, with nothing else going on. Every bit of num slides left by 8 positions. Whatever opens up on the right doesn't stay empty — it gets filled with brand-new zero bits.

Fig. 03a — 10 << 8: the value bits slide left, zeros fill in behind them

Green marks the four bits that actually carry 10's value (1010). Watch them: same four bits, same order, just relocated 8 places left. Amber marks the 8 brand-new zero bits that filled the gap behind them. Nothing was recalculated — the value bits simply moved, which is exactly why this conversion is exact, with zero rounding error, unlike the float path below.

Reading bits by hand: the powers-of-two chart

The same tool used for subnet masks in networking works here too — a row of column headers, each one a power of 2, doubling every step:

Fig. 03b — converting 10 to binary by hand, one power of 2 at a time

Decimal → binary: walk the columns left to right, asking "does this power of 2 still fit in what's left?" For 10: 128? no. 64? no. 32? no. 16? no. 8? yes, remainder 2. 4? no. 2? yes, remainder 0. 1? no. Binary → decimal is just the reverse: add up the powers of 2 sitting under every 1.

Connecting this straight back to the shift: every column here has a fixed power-of-2 value. << 8 doesn't touch those values — it slides every bit eight columns to the left, so whatever sat under 8 now sits under 2048, and whatever sat under 2 now sits under 512. Each bit's value gets multiplied by 2⁸ = 256, which is exactly why the whole number does too.

Doing it at the terminal with bc

bc converts between bases directly. echo "obase=2; 10" | bc prints 1010. echo "ibase=2; 1010" | bc prints 10. One gotcha: set ibase before obase if you need both — once ibase=2 is set, bc reads every number after it, including a subsequent obase value, as binary too.

Going back the other way: toFloat and toInt

float Fixed::toFloat( void ) const {
    return static_cast<float>(_fixedPoint) / (1 << fractionalBits);
}
int Fixed::toInt( void ) const {
    return _fixedPoint >> fractionalBits;
}

Both functions reverse the exact scale factor the constructors applied — but each one has to reverse it in a way that matches its own return type.

toInt() mirrors the int constructor exactly: >> is the inverse of <<, sliding every bit back to the right by fractionalBits positions. This is why truncation happens automatically and silently: any bits that represented fractional value simply fall off the right edge of the integer and are gone — there's nowhere for them to go once the shift discards them. toInt() never rounds; it always throws the fraction away.

toFloat() can't use a shift at all, for the same reason the float constructor couldn't — shifting is only meaningful for a type whose bits directly encode "value × 2ⁿ", and _fixedPoint is that type, but the result we want back is a float, which encodes numbers completely differently (mantissa and exponent). So the reversal has to happen through division instead: _fixedPoint / (1 << fractionalBits) undoes the earlier multiplication by 256.

Why static_cast<float> comes first

Without the cast, _fixedPoint / (1 << fractionalBits) is int / int — plain integer division, which truncates before a float ever enters the picture. 2560 / 256 gives the correct whole number 10 by luck, but something like 2600 / 256 would silently truncate to 10 instead of the correct 10.15625, losing the fraction before division even has a chance to preserve it. static_cast<float>(_fixedPoint) converts the numerator to a float first, so the division that follows is real floating-point division, keeping the fractional part intact.

Fig. 03c — reversing the conversion: toInt() shifts back, toFloat() casts then divides
The round trip isn't always exact

Fixed(3.14f) stores roundf(3.14 × 256) = 804. Calling toFloat() on that gives 804 / 256 = 3.140625 — not exactly 3.14 back. This is the precision half of the fixed-vs-float trade-off made concrete: with 8 fractional bits, the smallest representable step is 1/256 ≈ 0.0039, so any value that doesn't land exactly on a multiple of that step gets rounded to the nearest one representable, and stays rounded. This isn't a bug in toFloat() — it's a direct, visible consequence of choosing 8 fractional bits, and it's the same ε that ex02's increment/decrement operators step by.

The complete round trip, all four directions

_fixedPoint sits in the middle of everything, holding the raw representation the whole time — it's the one thing that never changes once set. Every constructor and conversion function exists purely to translate something familiar (int, float) into that raw form, or translate the raw form back into something familiar again.

int   → raw   :  num << fractionalBits                    // int constructor
float → raw   :  roundf(num * (1 << fractionalBits))    // float constructor
raw → int   :  raw >> fractionalBits                    // toInt()
raw → float :  raw / (1 << fractionalBits)              // toFloat()
DirectionExpressionExample inputResult

Why roundf specifically, worked through

The float → raw direction is the only one of the four that needs rounding at all — here's exactly why, with the numbers that make it concrete:

float f = 3.14f;
int raw = roundf(f * (1 << fractionalBits));

// f * 256        = 803.84   (scaled, but not a whole number)
// (int)803.84    = 803      (plain truncation — chops the .84, WRONG)
// roundf(803.84) = 804      (nearest whole number — CORRECT)
  • f * 256 — scales the float up by the usual factor, landing on 803.84.
  • plain truncation — casting straight to int without roundf would simply chop off everything after the decimal point, always rounding toward zero, giving 803 — the wrong nearest raw value.
  • roundf — picks whichever whole number is actually closest. 803.84 is closer to 804 than to 803, so that's what gets stored.

None of the other three directions need this: the int → raw shift is always exact (no fraction exists yet to lose), and both raw → int and raw → float are just reversing a scale factor on an already-whole raw integer — there's nothing left to round.

Why operator<< can't be a member function

A member function's implicit first parameter is always the object it's called on — the left-hand side. If operator<< were a member of Fixed, the only syntax that would type-check is a << std::cout;, with Fixed on the left. But the entire point is to write std::cout << a;, with the stream on the left. That forces operator<< to be a free function instead, taking the stream as its first parameter explicitly:

std::ostream &operator<<( std::ostream &o, const Fixed &f ) {
    o << f.toFloat();
    return o; // return by reference, so calls can chain
}

Returning std::ostream& is what makes std::cout << a << b << std::endl; legal at all — each << hands back the same stream, ready for the next one, the same reference-chaining reasoning behind why C++ functions return references in the first place.

Where friend would normally show up — and why you don't need it

In ordinary C++, a free operator<< that needs a class's private data is often declared friend inside the class. This module explicitly forbids friend. The way around it: implement operator<< using Fixed's own public interface — toFloat() — instead of reaching into _fixedPoint directly. If a class's public interface is complete enough, external functions rarely need special access at all; that's the encapsulation this restriction is quietly testing.

Sheet 04 · Exercise 02 — Now we're talking

Ad-hoc polymorphism: teaching operators to understand Fixed

The module's own title, spelled out: the same operator behaves differently depending on the types involved — decided entirely at compile time.

Polymorphism just means "many forms" — one name, several behaviors depending on context. Ad-hoc polymorphism (also called static or compile-time polymorphism) is the kind where the compiler decides which version to run purely by looking at the types of the operands, before the program ever runs. a + b compiles to a completely different instruction sequence depending on whether a and b are int or Fixed — there's no runtime lookup involved, no vtable, nothing dynamic. (The other kind — subtype polymorphism, decided at runtime through virtual functions — is what Module 04 introduces.)

Comparisons and arithmetic

Comparison operators return bool, and can compare raw bits directly — since both operands share the same fractional-bit scale, comparing the raw integers gives the exact same ordering as comparing the real values, with none of the surprises float comparison usually carries.

Arithmetic operators return a brand-new Fixed by value, and take their operand by const&:

Fixed Fixed::operator+( const Fixed &rhs ) const {
    return Fixed( this->toFloat() + rhs.toFloat() );
}

The trailing const promises + won't modify the object it's called on; const Fixed& avoids copying rhs just to read it; returning by value is required because the result is a genuinely new number that has to outlive this function call — there's no existing object to hand back a reference to.

Pre-increment vs post-increment

These look almost identical but do fundamentally different things, and the syntax exists specifically to tell the compiler which one you mean:

Fig. 04 — ++a modifies then returns itself; a++ saves, modifies, returns the old copy 
Fixed &Fixed::operator++() {              // pre: ++a
    _rawValue += 1;
    return *this;
}
Fixed Fixed::operator++( int ) {          // post: a++  — the unused int marks "postfix"
    Fixed old = *this;
    _rawValue += 1;
    return old;
}

That unnamed int parameter in the postfix version carries no value at all — it exists purely as a marker so overload resolution can tell prefix and postfix apart, since otherwise both would have the exact same signature. Pre-increment returns by reference because there's no new object — you're handing back the same one you just changed. Post-increment must return by value, because the object itself has already moved on; only the saved copy still holds the pre-increment value.

The step size, epsilon, is the smallest possible change to a Fixed: one raw bit, which represents 1/256 in real terms with 8 fractional bits. Incrementing is just _rawValue += 1 — no float math anywhere, which is precisely the kind of thing fixed-point representations make trivially exact.

Static min / max

static on a member function means it has no implicit this — it isn't "this object's minimum compared to another," it's a function that operates purely on the two arguments it's explicitly given, called as Fixed::min(a, b) rather than a.min(b). Two overloads exist — one taking Fixed&, one taking const Fixed& — so the right version gets picked automatically whether you're comparing mutable objects or const ones, exactly like the b and c in the subject's own example.

Both return a reference to whichever argument is smaller/larger — not a new copy. You get back an alias to one of the two objects you already had, which avoids an unnecessary copy and means the non-const version can still be used to modify whichever one "won."

Sheet 05 · Exercise 03 — BSP

Composition with const members, and a sign test

A Point made of two immutable Fixed coordinates, and a geometric test that decides inside vs outside using nothing but comparisons.

Point's two coordinates are declared Fixed const x and Fixed const y — and that immediately reconnects to a Module 01 rule: a const member has no legal "assign later," so x and y must be set in Point's constructor initializer list, exactly like the reference members from ex03 of Module 01. Same underlying rule, new context.

The design reasoning behind choosing const here, beyond the mechanical requirement: a Point represents one specific location. Once created, its coordinates shouldn't be able to silently drift — if you want a different location, you construct a different Point. That's the same immutable-value philosophy Fixed itself already follows.

The point-in-triangle test

The natural fit here, given everything Fixed can already compare and multiply, is a sign test using the 2D cross product. For each edge of the triangle, compute a value whose sign tells you which side of that edge's line the test point falls on. If the point lands on the same side for all three edges, it's inside.

For an edge from point P1 to P2, and a test point P, the sign check is:

cross = (P2.x - P1.x) * (P.y - P1.y) - (P2.y - P1.y) * (P.x - P1.x)

Run this once per edge (a→b, b→c, c→a). If all three results share the same sign, the point is inside. If any result is exactly zero, the point lies precisely on that edge's line — which the subject defines as outside (not strictly inside).

Fig. 05 — same sign on every edge = inside; a differing sign = outside

This is the actual payoff of ex01 and ex02: bsp() is implementable using only the public interface you already built — Fixed's +, -, *, and comparisons — never touching a raw integer directly. The whole class exists to make code like this read naturally.

Prototype is exact, same rule as Module 01

bool bsp( Point const a, Point const b, Point const c, Point const point ); — parameters by value, not const&. The subject fixes this signature exactly, same as zombieHorde back in Module 01: when a prototype is given, match it literally, regardless of what would otherwise be the "better" choice.
