Inheritance, from first principles

Not tied to any single exercise — this is everything about C++ inheritance worth having internalized before writing a derived class at all: what's actually inherited, how memory is laid out, why construction order isn't optional, what silently breaks when you copy by value, and what really happens at the point two base classes collide. One running example carries every section: Employee, specialized into Manager and Developer, recombined into TechLead.

Sheet 00

What inheritance actually is

One sentence carries the whole concept: a derived class is defined in terms of an existing class, and automatically acquires everything that class is willing to share.

Every employee at a company has an ID, a name, and a salary. A manager is an employee — that fact doesn't go away just because a manager also has direct reports. Rather than writing a whole new Manager class from scratch that happens to duplicate id, name, and salary, inheritance lets you say it directly: Manager is an Employee, plus a team size.

Fig. 00 — the is-a relationship, drawn the way UML draws it

Employee is the general case — the base class (also called parent class, or superclass). Manager and Developer are more specific cases — derived classes (also called child classes, or subclasses). The arrow in the diagram always points from specific to general, because that's the direction "is-a" reads: a Manager is-a Employee, never the other way around.

VocabularyAlso calledRole
Base classparent class, superclassthe general definition — Employee
Derived classchild class, subclassthe specialization — Manager

The syntax

class Manager : public Employee {
public:
    Manager(std::string name, int teamSize);
private:
    int _teamSize;
};

The colon introduces the base class list. public here is an access specifier that controls how Employee's own access levels carry through into Manager — covered fully in Sheet 04. For now, public is the form that preserves the is-a relationship exactly as written: anything you could do with an Employee from the outside, you can still do with a Manager.

Worth sitting with

Inheritance is not the only relationship between classes — it's specifically the is-a one. If Manager merely had a list of employees it manages, that would be composition (has-a), not inheritance, and the right tool would be a member variable, not a base class. Reach for inheritance only when the derived thing is genuinely a more specific version of the base thing — not merely something that uses it or contains it.

Sheet 01

What actually gets inherited

Not everything. Data and behavior come along automatically. The four special members that manage an object's own lifecycle do not.

When Manager inherits from Employee, every public and protected member of Employee — data members and member functions alike — becomes usable as if it had been declared directly inside Manager. You never retype _id, _name, _salary, or a getSalary() function; they're simply already there.

Member kindInherited automatically?Why
Data membersYesthey're part of the object's layout — see Sheet 02
Ordinary member functionsYescallable exactly as if declared in the derived class
Default constructorNoeach class defines its own; can explicitly call the base's, see Sheet 03
Copy constructorNosame reasoning — construction is per-class, not inherited
Copy assignment operatorNosame reasoning
DestructorNoeach class destroys its own additions; the base destructor still runs, but automatically, not by inheritance
Friend declarationsNofriendship is granted to a specific class, never transitive

This split makes sense once you notice the pattern: everything that describes what the object knows or can do is inherited. Everything that governs how the object comes into existence or goes out of existence is not — because those four members are exactly the Orthodox Canonical Form members from Module 02, and each class is responsible for its own.

Fig. 01 — what flows down automatically, and what every class must still write itself
Not the same as forbidden

"Not inherited" doesn't mean Manager's constructor can't use Employee's. It means the compiler won't write Manager's constructor for you the way it silently would for a completely standalone class. You still explicitly write Manager(...), and inside it you choose which of Employee's constructors to delegate to via the initializer list — that mechanism is the entire subject of the next sheet.

Sheet 02

Memory layout: the derived object physically contains the base

This is not a metaphor. A Manager object's first bytes in memory are a complete Employee object, sitting there as a genuine sub-object.

When you write class Manager : public Employee, the compiler doesn't generate some abstract relationship between two separate things. It lays out Manager's memory as: the entire Employee object first, followed immediately by whatever Manager itself adds.

Fig. 02 — a Manager object's memory: Employee's data first, Manager's own data appended

Two consequences follow directly from this layout, and both are worth having as reflexes:

sizeof grows

sizeof(Manager) is at least sizeof(Employee) plus whatever Manager adds — never smaller, since the base is fully embedded, not referenced.

The addresses coincide

For plain single inheritance, the address of a Manager object and the address of its embedded Employee sub-object are the same address — the base starts at offset 0.

This is exactly why a Manager* can be used anywhere an Employee* is expected without any conversion work at runtime — the compiler is simply reinterpreting the same address as "the Employee part of this," and for single inheritance that part genuinely starts right where the object does. (Multiple inheritance complicates this slightly, addressed in Sheet 08.)

Sheet 03

Construction and destruction order — the complete rule

Base before derived, always. Members initialize in declaration order, not the order you wrote them in the initializer list — the one part of this rule that actually surprises people.

Because a Manager object's memory starts with a complete Employee, that Employee part has to be fully built before anything Manager-specific can safely run. The language enforces this as a hard rule: the base class's constructor runs to completion first, then the derived class's own constructor body executes.

Fig. 03 — construction runs outward from the base; destruction unwinds in the opposite order 
Manager::Manager(std::string name, int teamSize)
    : Employee(name), _teamSize(teamSize)
{
    std::cout << "Manager built" << std::endl;
}

Employee(name) in the initializer list picks which base constructor runs as step one. Omit it entirely and the compiler tries to call Employee's default constructor automatically — which fails to compile if Employee has no default constructor available.

The gotcha: initializer list order is not execution order

This is the single most commonly misunderstood rule in the whole topic. Members — and base classes, when there are several — are always initialized in the order they're declared in the class body, never in the order you happen to write them in the initializer list. Writing the initializer list in a different order doesn't change execution order; it just makes the code misleading to read, and most compilers warn about exactly this (-Wreorder).

Fig. 03b — the initializer list is written in one order but executes in declaration order
Why this matters in practice

If _a's initializer reads _b's value, expecting _b to already be set because it appears first in the initializer list, you get undefined behavior — _b may not have been initialized yet, because declaration order says _a actually runs first here. The fix isn't clever code, it's discipline: write the initializer list in the same order the members are declared, every time, so the two orders always visually agree.

With multiple base classes (Sheet 08), the same rule extends: bases are constructed in the order they appear in the class header's base list — class TechLead : public Manager, public Developer always constructs Manager before Developer, regardless of what order the initializer list writes them in.

Sheet 04

Access control across inheritance

The access specifier on the base class list isn't decoration — it changes what a derived class's own users are allowed to see.

Module 02 only needed two access levels: private and public. Inheritance is the reason protected exists at all: a derived class needs to touch its base's data directly, but the outside world still shouldn't. And the access specifier on the inheritance itself — public Employee, protected Employee, or private Employee — controls how far down that visibility continues past the derived class.

The row that surprises people

Employee's private members are never accessible from Manager, under any inheritance mode. They still exist — they're still physically part of the memory layout from Sheet 02 — but Manager's own code has no name to reach them by. Only Employee's own member functions can touch them. This is precisely why the exercise-facing sheet flagged the private vs protected decision as consequential: choose private in the base, and every derived class is permanently locked out, no matter what inheritance mode it uses.

Fig. 04 — public inheritance (the common default) leaves the base's own access levels untouched from the outside

protected and private inheritance exist for narrower cases — typically implementing one class purely in terms of another without exposing that fact to the outside world, breaking the is-a relationship on purpose. In practice, the overwhelming majority of inheritance you'll write uses public, because it's the mode that keeps "a Manager is usable anywhere an Employee is expected" actually true from outside code.

Sheet 05

Name hiding — wider than it looks

Redeclare one member with a name that exists in the base, and every overload of that name in the base disappears from view — not just the one with the matching signature.

Say Employee has two overloads of describe:

class Employee {
public:
    void describe() const;          // prints name and salary
    void describe(bool verbose) const; // prints extra detail if true
};

Now Manager declares its own describe(), with no arguments, to add a line about team size:

class Manager : public Employee {
public:
    void describe() const; // only this one overload
};
The surprise

Manager m(...); m.describe(true); fails to compile. Not because the types are wrong — because Manager's declaration of describe() hides the entire name describe from Employee, including the bool overload that Manager never touched. Name lookup in C++ resolves the name first, in the nearest enclosing scope, and only then considers overloads within whatever it found there. Once it finds Manager::describe(), it stops looking upward entirely — it never even reaches Employee::describe(bool) to consider it as a candidate.

Fig. 05 — redeclaring one overload hides the entire name, not just that overload

The fix: a using-declaration

Pull the hidden overloads back into scope explicitly:

class Manager : public Employee {
public:
    using Employee::describe; // bring back every hidden overload of describe
    void describe() const;      // Manager's own version still takes priority for this exact signature
};

Fully qualifying the call also works without touching the header at all: m.Employee::describe(true); bypasses lookup's early stop entirely by naming the scope directly. Either approach fixes it; the using-declaration is the more common idiom when you actually want both overloads reachable through ordinary, unqualified calls.

Sheet 06

Static binding: why redefining isn't overriding, yet

Without the virtual keyword, which version of a function runs is decided by the pointer's declared type, not by what the object actually is underneath.

Say both Employee and Manager define describe(), with the same signature this time — Manager::describe() genuinely redefines Employee::describe(), the way ex01's ScavTrap::attack() redefined ClapTrap::attack(). Called directly on a Manager object, or through a Manager*, you get Manager::describe() — unsurprising.

Manager m("Alice", 5);
m.describe();          // Manager::describe() — obviously

Employee *ptr = &m;    // a Manager, viewed through an Employee pointer
ptr->describe();       // which one actually runs?
The answer, without virtual

ptr->describe() calls Employee::describe() — the base version — even though the object ptr points at is genuinely a Manager. This is called static binding (or early binding): the compiler decides which function to call at compile time, purely by looking at the declared type of the expression — here, Employee* — without any regard to what the object turns out to be when the program actually runs.

Fig. 06 — the pointer's declared type decides which function runs, not the object it actually points to

This isn't a bug — it's the default resolution rule for ordinary member functions, and it's consistent with how the rest of the language works before you opt into anything dynamic. The compiler generates the call to Employee::describe() at the point of ep->describe() because that's the only information it has: the static, compile-time type of ep.

The fix belongs to the next chapter

Marking describe() as virtual in Employee flips this entirely: the call becomes resolved by the object's actual type at runtime, regardless of what pointer type you're holding it through. That's dynamic binding (or late binding), and it's the mechanism true polymorphism is built on — the subject of the next module. Everything in this sheet describes the behavior you get without that keyword, which is the behavior every inherited function has by default.

Sheet 07

Object slicing

Copy a derived object into a base object by value, and the derived-only part doesn't come along for the ride — it's silently cut off.

Manager is a complete Employee plus a _teamSize. But Employee has no _teamSize field to copy into — it was never declared to have one. So when you copy a Manager into a plain Employee variable, only the part that actually fits gets copied.

Manager m("Alice", 5);
Employee e = m; // SLICING — only the Employee part of m is copied into e

std::cout << e.getName(); // "Alice" — fine, this part exists in Employee
// e has no way to ask about team size at all — that data never made it in
Fig. 07 — only the Employee-shaped portion of Manager survives the copy into e

This is called object slicing, and the compiler never warns about it — Employee e = m; is completely legal, ordinary copy-construction. It's dangerous specifically because it's silent: e is not "a Manager pretending to be an Employee," it's a genuine, fully-formed Employee, and there's no way to ask it for the team size afterward, because that data was never copied in the first place.

Where it bites

A function parameter taken by value as Employee silently slices every Manager or Developer passed to it — even though the call itself compiles cleanly with no warning at all.

How to avoid it

Take the parameter by reference or pointer — const Employee& or Employee* — instead of by value, whenever the function might receive a derived object and needs to preserve what it actually is.

This is exactly why the bsp() prototype back in Module 02 mattered so much for matching literally — parameters by value vs by reference aren't interchangeable stylistic choices once inheritance and polymorphism are involved. A by-value parameter of a base type is an implicit promise to slice anything derived that gets passed to it.

Sheet 08

Multiple inheritance

A class can inherit from more than one base at once. The mechanics mostly extend cleanly from everything above — until two bases share a name, or a common ancestor.

Say a TechLead is genuinely both things at once: manages people and writes code. C++ allows exactly this, listing multiple bases separated by commas:

class TechLead : public Manager, public Developer {
public:
    TechLead(std::string name, int teamSize, std::string language);
};
Fig. 08 — TechLead combines two independent bases into one object

Everything from Sheets 02–04 still applies, doubled: TechLead's memory contains a complete Manager sub-object followed by a complete Developer sub-object; both base constructors run before TechLead's own body, in the order the bases are listed in the class header — Manager, then Developer, regardless of initializer-list order; destruction is the exact reverse.

The new failure mode: name collisions

If both Manager and Developer declare a member with the same name — say both have their own describe() — an unqualified call from inside TechLead is genuinely ambiguous. There are two equally valid candidates, and unlike the single-inheritance name-hiding case in Sheet 05, neither one hides the other here — they arrive from two independent, unrelated bases, so the compiler can't prefer either one and simply refuses to compile until you disambiguate.

tl.describe();              // ERROR: ambiguous — Manager::describe or Developer::describe?
tl.Manager::describe();     // OK — explicitly qualified

// or, inside TechLead itself, pick one to be the default:
using Manager::describe;

This is a different problem from the diamond case in the next sheet, which involves a name that traces back to a genuinely shared ancestor. Here, Manager::describe() and Developer::describe() are unrelated functions that simply happen to share a spelling — the fix is exactly the qualification syntax already familiar from Sheet 05.

Sheet 09

The diamond problem, and virtual inheritance

Both TechLead's bases already inherit from the same grandparent. Draw the arrows and the shape becomes obvious — and so does the problem.

Manager inherits from Employee. Developer inherits from Employee. TechLead inherits from both Manager and Developer. Four classes, four arrows, and the shape they trace out is a diamond — which is exactly where the name for this problem comes from.

Fig. 09a — without virtual inheritance, Employee gets built twice inside one TechLead

Without any special handling, TechLead ends up containing two entirely separate Employee sub-objects — one via the Manager path, one via the Developer path. This is worse than the ordinary name-collision case from Sheet 08: it's not just that a name is ambiguous, it's that the underlying data is physically duplicated. tl.getSalary() doesn't just have two candidate functions to choose from — there are genuinely two different _salary fields in memory, and nothing keeps them in sync.

The fix: virtual on the inheritance itself

This is a different use of virtual from the one in Sheet 06 — there it marked a function for dynamic dispatch; here it marks a base class relationship as shared:

class Manager   : virtual public Employee { /* ... */ };
class Developer : virtual public Employee { /* ... */ };

virtual public Employee tells the compiler: however many separate paths lead back to Employee, keep exactly one shared sub-object, no matter how many derived classes route through it.

Fig. 09b — with virtual inheritance, both paths converge on one shared Employee
The trade-off: construction responsibility moves

Sharing the base changes who is responsible for building it. Normally, Manager's own initializer list calling Employee(name) is exactly what constructs the base. With a virtual base, that call is ignored whenever Manager is being constructed as part of something further derived, like TechLead. Instead, the most-derived class — TechLead itself — becomes directly responsible for constructing the shared virtual base, bypassing both intermediate classes' own base-constructor calls entirely. This is a genuine special case in the language: normally a class never reaches past its immediate base to construct a grandparent directly, but virtual inheritance requires exactly that.

TechLead::TechLead(std::string name, int teamSize, std::string language)
    : Employee(name),           // TechLead builds the shared base directly
      Manager(name, teamSize),  // Manager's own Employee(name) call is ignored here
      Developer(name, language) // so is Developer's
{ /* ... */ }

That last row is worth knowing exists even without needing the implementation details: virtual inheritance isn't free. Making a base virtual adds a small amount of indirection so that Manager's view of the shared Employee and Developer's view of it can agree on the same memory even though each was compiled somewhat independently. It's exactly why virtual isn't the default for every base class — only reach for it when a genuine diamond shape is actually forming.
