Sheet 00

The big picture

Module 01 is really one idea taught seven times: who owns a piece of memory, and how long do they own it for.

In C, you managed memory with malloc/free and raw addresses. Module 00 introduced std::string and classes, which hide most of that. Module 01 pulls the curtain back: new/delete, pointers and references are all different answers to the same question: Where does this object live and who is responsible for it?

Rule to internalize

Every new needs exactly one delete. Every new[] needs exactly one delete[]. Mixing them (delete on an array, or forgetting the delete entirely) is undefined behavior

Sheet 01 · Exercise 00 — BraiiiiiiinnnzzzZ

Stack vs heap

The exercise's real question: in which case is it better to allocate on the stack, and in which case the heap?

A stack object's lifetime is tied to its scope. The compiler constructs it and destroys it automatically. A heap object's lifetime is tied to nothing but your own delete call. It survives past the function that created it, which is exactly why you'd reach for it when something needs to be handed back to a caller.

Fig. 01 — a stack zombie vs a heap zombie in the same function

Default: reach for the stack. Only go to the heap when you have a concrete reason the object must outlive its creating scope, and once you do, the delete is your responsibility, not the compiler's.

Sheet 02 · Exercise 01 — Moar brainz!

Single allocation, many objects

Zombie* zombieHorde(int N, std::string name) — N objects, one allocation, one pointer back to the first.

"Single allocation" is the operative phrase. Calling new Zombie(...) N times in a loop would give you N separate allocations scattered wherever the heap happens to put them — and you'd need to track N different pointers to free them all. The array form of new, written new Zombie[N], does something different: it asks the heap for one contiguous block big enough for N objects, and hands you back a single pointer to the first one. Pointer arithmetic (horde + i) or array indexing (horde[i]) gets you to the rest.

Fig. 02 — new Zombie[N] vs N separate new calls
Gotcha

Array new can't forward constructor arguments in C++98 — new Zombie[N](name) is not valid syntax. If Zombie's only constructor takes a name, new Zombie[N] won't compile as-is. This is the actual design decision the exercise is testing: either give Zombie a default constructor and set the name afterward through a setter, in a loop over the allocated block, or reconsider whether array-new is even the right tool here. Worth sitting with before writing any code.

Pairing rule

Whatever you allocate with new[] must be freed with delete[], never plain delete. The array form calls the destructor on every element before freeing the block; a bare delete on an array pointer only runs the first element's destructor and produces undefined behavior. This is exactly the kind of thing valgrind will catch and a quick visual read-through won't.

Sheet 03 · Exercise 02 — HI THIS IS BRAIN

Pointers vs references

Coming from C you already know pointers. The reference is the genuinely new idea here, and it's an easy one to tangle up with the phrase "pass by reference," which gets used loosely even when what's actually happening under the hood is passing a pointer.

A reference is not a separate object at all. It's an alias, a second name for a variable that already exists. Nothing gets allocated, nothing gets copied. Once it's bound, it can never point anywhere else and it can never be null, because there's no separate "it" to begin with, just another label on the same variable.

int score = 10;
int &nickname = score;   // nickname is just another name for score

nickname = 20;                    // changes score too, they're the same variable
std::cout << score;               // prints 20
In plain terms

Think of it like calling someone by a nickname. The nickname isn't a second person standing next to them, it's just another way to refer to the one person who's there. Change what the nickname points to and you've changed the original directly, because they were never two things.

A pointer is a genuinely different object. It has its own address and its own storage, and what it holds is another variable's address, a value you're free to change:

int *scorePtr = &score;   // scorePtr holds the address of score

*scorePtr = 30;                    // dereference to reach score and change it
scorePtr = &otherVar;             // reseat it: now it points somewhere else entirely

That's the whole difference in one line: a pointer is a box that holds an address and can be emptied or refilled; a reference isn't a box at all, just a second label taped onto a box that already exists.

C has no version of this at all, and that's not an oversight, it's a design choice. C's whole philosophy keeps indirection visible: an address is always a value sitting in a variable you can see, print, reseat, or set to null, nothing ever hides that a pointer is a pointer. C++ added references specifically to break that visibility on purpose, in exchange for two things C didn't prioritize: overloaded operators that read like plain expressions instead of pointer-juggling function calls, and function parameters you can modify without pointer syntax showing up at the call site. References aren't a newer feature C forgot to add, they conflict with a rule C set on purpose. The closest C gets is a pointer you dereference by hand every single time you touch it:

/* the same idea, in C */
int score = 10;
int *nickname = &score;

*nickname = 20;             // the * is mandatory here, C won't insert it for you
printf("%d", score);     // prints 20
Under the hood

On most compilers a C++ reference compiles down to exactly that: an address stored somewhere, dereferenced automatically on every access. It isn't a different runtime mechanism from a pointer, it's the compiler agreeing to insert the * for you and refusing to ever let the address be null or reseated. The safety is a compile-time contract, not a hardware feature.

Sheet 04 · Exercise 03 — Unnecessary violence

Composition, and choosing pointer vs reference as a member

The subject asks you to think about this before coding: when is a pointer to Weapon the right call, and when is a reference?

HumanA and HumanB both have a Weapon. That "has-a" relationship is composition, the object-oriented sibling of the encapsulation you already used in PhoneBook. What differs is a guarantee each class needs to make about that relationship, and the member type follows directly from the guarantee:

HumanA — always armed

Takes its Weapon in the constructor and is guaranteed to always have one. A reference member fits: it must be bound the moment the object is constructed (init list, not the constructor body), it can never be null, and it can never be pointed somewhere else afterward. That's not a limitation here — it's the guarantee "always armed" is asking for, enforced by the compiler instead of by convention.

HumanB — maybe armed

Doesn't take a Weapon at construction, and might not have one at all, or might get one later via setWeapon(). A pointer member fits: it can start out null (no weapon yet), and it can be reassigned when setWeapon() is called. Neither of those is possible with a reference.

Also worth noticing

getType() is specified to return a constant reference to type, not a copy. That avoids copying the string on every call while still preventing the caller from modifying the original through the returned reference — the same read-only guarantee your const getters in Contact gave you, just applied to the return value instead of the method itself.

Sheet 05 · Exercise 04 — Sed is for losers

File streams, without C functions

Open, read, transform, write — entirely through <fstream> and std::string, no fopen/fread in sight.

std::ifstream and std::ofstream are the C++ replacements for fopen-style file handles — they're RAII objects, so the file is opened in the constructor and closed automatically in the destructor. The pattern you'll lean on:

std::ifstream in(filename.c_str());
if (!in.is_open()) { // handle the error — don't assume the file exists }
std::string content((std::istreambuf_iterator<char>(in)), std::istreambuf_iterator<char>());

That last line reads the entire file into one string in a single pass, which matters here because the exercise wants you to replace every occurrence of s1 with s2 across the whole file, not line by line where a match could straddle a newline.

The catch

std::string::replace is explicitly forbidden. The other string members are fair game though — find() to locate each occurrence and substr() to build the output piece by piece around it is the standard route: find the next match, append everything before it plus s2 to a result string, advance your search position past the match, repeat until find() returns std::string::npos.

Edge cases worth testing yourself, since the subject asks for your own tests: an empty file, s1 not present at all, s1 and s2 being the same string, and s1 occurring at the very start or end of the file.

Sheet 06 · Exercise 05 — Harl 2.0

Pointers to member functions

The goal stated directly in the subject: dispatch without a forest of if/else if/else.

A pointer to a member function isn't like a regular function pointer, it can't be called on its own, because a member function implicitly needs an object (a this) to run against. The syntax reflects that: it's a pointer scoped to the class, and calling it requires supplying an object alongside it.

void (Logger::*handler)(void) = &Logger::warn;
(myLogger.*handler)();      // via an object
(this->*handler)();         // via this, from inside a member function
  • void (Logger::*handler)(void) — declares handler as "a pointer to a member function of Logger, taking no args, returning void." The Logger:: inside the parens is what makes this a member-function pointer instead of an ordinary function pointer.
  • &Logger::warn — you must qualify with the class name here, even from inside the class itself. Just &warn won't compile.
  • .* and ->* — the "pointer-to-member" dereference operators. They bind the function pointer to an actual object before the call happens, which is the missing this a member function needs.

For Harl, this generalizes into an array: four pointers-to-member-functions, one per level, indexed in the same order as the levels. complain(level) then becomes "find the index for this level string, call (this->*array[index])()" — no branching on behavior at all, just a lookup.

Why debug/info/warning/error are private

Only complain() should be a valid entry point from outside the class — callers pick a level, not a specific rant. Keeping the four level methods private and dispatching through one public method is the same encapsulation instinct as Contact's getters/setters, just applied to behavior instead of data.

Sheet 07 · Exercise 06 — Harl filter (optional)

Switch statements & fallthrough

"Display all messages from this level and above" is a fallthrough problem in disguise.

switch jumps to the matching case label and then keeps executing forward through every subsequent case until it hits a break. It doesn't stop at the end of the matched case on its own. That's usually the bug you guard against with a break in every case. Here it's the feature: if levels are ordered DEBUG → INFO → WARNING → ERROR and you omit the break, matching WARNING and falling through naturally prints WARNING and everything below it.

Fig. 05 — matching WARNING falls through to ERROR when there's no break
Second half of the exercise

The subject also wants a fallback for input that doesn't match any known level — that's switch's default: case, which catches anything the earlier case labels didn't. Since switch only works on integral types (not std::string directly in C++98), you'll need to map the level string to an int first — an index or an enum — before the switch can dispatch on it.
